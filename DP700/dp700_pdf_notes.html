🏠 Lakehouse Architecture

What is a Fabric Lakehouse?

A Lakehouse combines a data lake (flexible storage for any file format) with a data warehouse (analytical SQL querying) — all built on OneLake. Every piece of data lives in one place; different engines just read it differently.

  • All Tables are stored as Delta format (Parquet + _delta_log) — auto-registered in the metastore
  • Files section = raw landing zone; any format (CSV, JSON, Parquet, images…); not auto-registered
  • Powered by Apache Spark runtime; also queryable via SQL analytics endpoint (read-only T-SQL)
  • Every lakehouse also gets a default semantic model for Power BI (no longer auto-created for new lakehouses as of Sep 2025)
SQL analytics endpoint is read-only. You cannot INSERT, UPDATE, or DELETE through it. Write operations must go through Spark, pipelines, or dataflows.

Two Top-Level Folders

FolderPurposeAuto-registered as table?Shortcut placement
Tables/Managed Delta tables✅ Yes (Delta only)Top level only (no subdirs)
Files/Unmanaged raw files❌ NoAny level of hierarchy
Only Delta tables appear in the SQL analytics endpoint. Parquet, CSV, and other formats are NOT queryable through it. If you don't see your table, convert it to Delta first.

Lakehouse vs. Data Warehouse — Quick Comparison

FeatureLakehouseData Warehouse
Primary toolApache Spark (Python, Scala, SQL, R)T-SQL
Data typesStructured and unstructuredStructured only
Multi-table transactions❌ No✅ Yes
Data ingestionNotebooks, pipelines, dataflows, shortcutsCOPY INTO, INSERT, CTAS, pipelines
Best forData engineering, data science, medallionBI reporting, dimensional modeling, SQL-first
Storage formatDelta on OneLakeDelta on OneLake
Both Lakehouse and Warehouse store data in Delta format on OneLake. They differ in the tools and access patterns, not the underlying storage.

Lakehouse Schemas

Schemas are optional and must be enabled at creation time (enabled by default for new lakehouses). Schema-enabled lakehouses allow:

  • Organizing tables by domain: sales.orders, marketing.campaigns
  • Granting access at schema level
  • Cross-workspace 4-part queries: workspace.lakehouse.schema.table
  • Schema shortcuts — map a schema to a folder in ADLS Gen2 or another lakehouse
  • Advanced features like materialized lake views (require schema-enabled)
OneLake RLS/CLS enforcement in Spark requires the default lakehouse to be schema-enabled (or no default lakehouse set). If using a non-schema lakehouse, set Spark property spark.sql.fabric.catalog.enable-schemaless-lakehouses=true in the environment.

SQL Analytics Endpoint

  • Auto-provisioned when you create a lakehouse
  • Read-only T-SQL interface — explore, report, and ad-hoc query
  • Exposes all Delta tables (including tables reached via shortcuts)
  • Does NOT expose non-Delta files (Parquet, CSV, etc.)
  • Connect Power BI directly — build reports without a separate warehouse
  • Does NOT support full T-SQL DML; use Spark for writes
  • Use Analyze data with → SQL analytics endpoint from the lakehouse ribbon

Analyze Data Options (Lakehouse Ribbon Dropdown)

OptionEngineUse Case
SQL analytics endpointT-SQL (read-only)SQL queries, Power BI reports
Eventhouse endpointKQLHigh-performance real-time analytics
Notebook (New / Existing)Apache SparkExploration, transformation, data science

Automatic Table Discovery

When you place files in the Tables/ folder, Fabric automatically validates, extracts metadata, and registers the table in the metastore — no CREATE TABLE needed. Works for Delta format only; other formats land in the Unidentified area.

Unidentified items appear when: broken shortcuts, non-Delta content written programmatically to Tables/, or nested subfolders that don't follow Delta table structure.

📂 OneLake Shortcuts

What are Shortcuts?

Shortcuts are pointers — they make external data appear as local tables or folders without copying the data. Think of them as symbolic links that span storage boundaries.

Supported Shortcut Sources

Internal Sources (use caller identity)

  • Lakehouses
  • Warehouses
  • KQL databases
  • Mirrored databases
  • SQL databases
  • Semantic models

External Sources (use cloud connection credentials)

  • Azure Data Lake Storage Gen2
  • Azure Blob Storage
  • Amazon S3
  • Amazon S3-compatible storage
  • Google Cloud Storage
  • Dataverse
  • OneDrive & SharePoint
  • On-premises data gateway (OPDG)
  • Iceberg tables

Shortcut Caching Rules

OneLake caches shortcut data locally for supported sources. This is important for performance and exam questions:

SourceCached?
Amazon S3✅ Cached
Google Cloud Storage (GCS)✅ Cached
S3-compatible storage✅ Cached
On-premises data gateway (OPDG)✅ Cached
Azure Data Lake Storage Gen2❌ NOT cached
Azure Blob Storage❌ NOT cached
ADLS Gen2 and Azure Blob shortcuts are NOT cached. S3, GCS, S3-compatible, and OPDG are cached. This is a common exam trap — Microsoft-native Azure sources are not cached; non-Azure external sources are.

Access Control for Shortcuts

  • Internal shortcuts: Use the calling user's identity. User must have read permissions on the target.
  • External shortcuts: Use cloud connection credentials set at shortcut creation time. Any user with lakehouse access can read through the shortcut using the stored credentials.

Shortcuts vs. Copying Data — When to Use Each

ScenarioUse
Data already in Fabric (another lakehouse/warehouse)Shortcut
External cloud storage, near-real-time access neededShortcut
Complex transforms needed before useCopy + transform
Compliance requires data in specific regionCopy (shortcuts don't move data)
Need full schema evolution and maintenance controlCopy (Delta maintenance only on local tables)

⚡ Delta Lake — Core Concepts

What Delta Lake Adds to Parquet

  • ACID transactions — atomicity, consistency, isolation, durability
  • Transaction log (_delta_log/) — every commit creates a new version entry
  • Time travel — query any past version or timestamp
  • Schema enforcement & evolution
  • Upserts (MERGE)
  • Change Data Feed (CDF) — row-level change tracking
  • Deletion vectors — soft-delete rows without rewriting files

Key Commands Summary

CommandPurposeExam Key Rule
OPTIMIZECompacts small files into larger onesImproves read performance; also applies V-Order & Z-Order
VACUUMRemoves unreferenced files from storageDefault 7-day retention; permanently deletes from OneLake
REORG ... APPLY (PURGE)Physically removes deletion vector rowsOPTIMIZE does this automatically when >5% rows are deletion-vector-deleted
DESCRIBE DETAILShows table metadata (files, size, location)Read-only inspection; works in Spark & SQL endpoint
DESCRIBE HISTORYAudit log of all transactionsUse to find version for time travel or RESTORE
RESTORE TABLE ... TO VERSION AS OFRolls table back to a prior versionMakes an older version the new current state

🗜️ OPTIMIZE — File Compaction

Basic Usage

-- Basic compaction
OPTIMIZE table_name

-- With Z-Order (colocate rows with similar column values)
OPTIMIZE table_name ZORDER BY (column1, column2)

-- With V-Order (optimized Parquet encoding for reads)
OPTIMIZE table_name VORDER

-- Both Z-Order + V-Order in one pass
OPTIMIZE table_name ZORDER BY (column1, column2) VORDER

OPTIMIZE Execution Order

When combining options, Spark applies in this sequence: bin compaction → Z-Order → V-Order

V-Order Behavior with OPTIMIZE

How you invoke OPTIMIZEV-Order behavior
OPTIMIZE table VORDERForces V-Order on rewritten files regardless of session or table settings
OPTIMIZE table (no VORDER keyword)Inherits from TBLPROPERTIES("delta.parquet.vorder.enabled") if set, else falls back to session config

When to Run OPTIMIZE

  • After large batch ingestion jobs
  • When many small files accumulate and reads slow down
  • Queries filter frequently on 2+ columns together → add ZORDER BY
OPTIMIZE is idempotent — safe to run repeatedly. It only rewrites files that benefit from compaction (minFileSize default = 1 GB, maxFileSize default = 1 GB).
Z-Order is best when queries filter on multiple columns AND those filters are selective enough to skip files. Don't use Z-Order on low-cardinality columns — it wastes time with no benefit.

Fast Optimize

Intelligently skips compaction operations that won't meaningfully improve performance — evaluates each candidate bin before deciding to compact.

SET spark.microsoft.delta.optimize.fast.enabled = TRUE

Auto-Compaction

Delta supports automatic compaction after writes via table properties or workspace settings — keeps tables healthy without manual maintenance jobs.

🧹 VACUUM — Storage Cleanup

What VACUUM Does

VACUUM permanently deletes unreferenced Parquet files from OneLake. It only removes files that meet BOTH conditions:

  • The file is no longer referenced by the Delta log (replaced by a newer version)
  • The file is older than the configured retention threshold
VACUUM permanently deletes files from OneLake. It does NOT improve query performance — its purpose is storage cleanup only. Use OPTIMIZE for query performance.

Retention Rules

  • Default retention = 7 days (168 hours)
  • Fabric portal/API maintenance requests fail by default for retention < 7 days
  • To use shorter retention: set spark.databricks.delta.retentionDurationCheck.enabled = false
  • Delta log retention = 30 days default (delta.logRetentionDuration table property)

VACUUM Syntax Variants

-- Default 7-day retention
VACUUM table_name

-- Custom retention (e.g., 7 days exactly = 168 hours)
VACUUM table_name RETAIN 168 HOURS

-- Preview files that would be deleted (no actual deletion)
VACUUM table_name DRY RUN

-- Combine preview with custom retention
VACUUM table_name RETAIN 168 HOURS DRY RUN

-- LITE mode: faster, uses only Delta log (not full directory listing)
-- Requires Fabric Spark runtime 2.0+
VACUUM table_name LITE

VACUUM and Time Travel — Critical Link

VACUUM breaks time travel. If VACUUM removes old files, you can no longer query those older table versions even if they still appear in DESCRIBE HISTORY. Time travel availability depends on: (1) log retention AND (2) physical file existence.
SettingDefaultControls
delta.logRetentionDuration30 daysHow long Delta log entries are kept
VACUUM retention7 daysHow long unreferenced data files exist on disk

The oldest queryable version = min(log retention, file retention). In practice: VACUUM's 7-day default is the limiting factor.

Where to Run VACUUM

  • ✅ Fabric notebooks
  • ✅ Spark job definitions
  • ✅ Lakehouse Maintenance UI / pipeline Lakehouse Maintenance activity
  • ❌ SQL analytics endpoint (does NOT support Spark Delta maintenance commands)
  • ❌ Warehouse SQL editor
Run VACUUM on a regular cadence (e.g., weekly or after major compaction cycles). Use DESCRIBE DETAIL to monitor file count before and after.
Source: fabric-data-engineering.pdf — "VACUUM Delta tables", "Run Delta table maintenance in Lakehouse" (MS Learn, May 2026)

🎨 V-Order — Write-Time Parquet Optimization

What V-Order Is

V-Order is a write-time optimization for Parquet files that reorganizes row-group distribution, encoding, and compression to improve read performance across all Fabric engines (Power BI Direct Lake, SQL analytics endpoint, Spark).

  • Files remain open-source Parquet compliant (readable by any Parquet-compatible tool)
  • Typical impact: ~15% slower writes, up to 50% better compression, significant read speedup
  • Best for read-heavy patterns: dashboards, interactive analytics, repeated scans

V-Order Default Status (CRITICAL FOR EXAM)

Workspace creation dateV-Order defaultOptimize Write default
Before April 2025Enabled by defaultEnabled by default
After April 2025 (Runtime 1.3)Disabled by defaultDisabled by default
Runtime 2.0DisabledUNSET (false)
V-Order is disabled by default in all newly created Fabric workspaces (post April 2025). You must explicitly enable it. Do not assume it's on.

Controlling V-Order at Different Levels

LevelConfig / PropertyScope
SessionSET spark.sql.parquet.vorder.default=TRUEAll Parquet writes in current session
TableTBLPROPERTIES("delta.parquet.vorder.enabled" = "true")All future writes to that specific table
Write operation.option("parquet.vorder.enabled","true")Single write only
Precedence: Write operation level > Session level > Table property level. If you set V-Order at the session level to true, it applies to ALL Parquet writes in that session, even if TBLPROPERTIES says false.

V-Order Does NOT Affect Existing Files

Changing V-Order settings (via session config, table property, or ALTER TABLE) only affects future writes. To apply V-Order to existing files, run OPTIMIZE table VORDER.

⏰ Time Travel

Querying Historical Versions

-- Query by version number
SELECT * FROM table_name VERSION AS OF 5

-- Query by timestamp
SELECT * FROM table_name TIMESTAMP AS OF '2024-01-01'

-- Find available versions and timestamps
DESCRIBE HISTORY table_name

-- Limit history output
DESCRIBE HISTORY table_name LIMIT 10

Time Travel vs. RESTORE

FeatureWhat it doesModifies table?
Time travelRead-only query against an older snapshot❌ No
RESTORE TABLEMakes an older version the new current state✅ Yes
Pattern: Use time travel first to inspect the data, then use RESTORE only if you want to roll back the table.

What Limits Time Travel Availability

  1. Transaction log retention (delta.logRetentionDuration — default 30 days)
  2. Physical file retention (VACUUM — default 7 days)

The oldest queryable version = minimum of both. In practice, VACUUM's 7-day window is the binding constraint.

Time Travel in Different Engines

  • ✅ Fabric notebooks (Spark SQL / PySpark)
  • ✅ Spark job definitions
  • ✅ SQL analytics endpoint (limited — subject to VACUUM retention)
  • ❌ Warehouse SQL editor
Source: fabric-data-engineering.pdf — "Time travel", "VACUUM Delta tables" (MS Learn, May 2026)

📡 Change Data Feed (CDF)

What CDF Does

CDF records row-level changes (insert, update, delete) for a Delta table after it's enabled. Use it to build incremental ETL pipelines that process only what changed.

Enable CDF

-- Enable at table creation
CREATE TABLE sales.orders (
  order_id BIGINT, customer_id BIGINT, order_total DECIMAL(18,2)
)
USING DELTA
TBLPROPERTIES (delta.enableChangeDataFeed = true)

-- Enable on existing table
ALTER TABLE sales.orders
SET TBLPROPERTIES (delta.enableChangeDataFeed = true)

Read Change Data

-- Read from a specific version onward
SELECT * FROM table_changes('table_name', 1)

-- Read a bounded version range
SELECT * FROM table_changes('sales.orders', 120, 125)

-- Read by timestamp range
SELECT * FROM table_changes(
  'sales.orders',
  TIMESTAMP '2026-05-01T00:00:00Z',
  TIMESTAMP '2026-05-01T23:59:59Z'
)

CDF Output Columns

ColumnValuesDescription
_change_typeinsert, update_preimage, update_postimage, deleteThe type of change
_commit_versionIntegerDelta table version when change was committed
_commit_timestampTimestampWhen the commit happened

Critical CDF Rules

CDF does NOT backfill historical changes. It only captures changes that happen after the property is enabled. Enable it early in the table lifecycle.
UPDATE and MERGE produce BOTH update_preimage (before) AND update_postimage (after) rows — useful for auditing what changed.
OPTIMIZE and REORG do NOT produce CDF records (dataChange = false). Maintenance ops won't pollute your change feed.

CDF Storage Impact

CDF writes extra files to a _change_data folder. These are subject to VACUUM — older CDF files are removed when they fall outside the retention window.

Source: fabric-data-engineering.pdf — "Use change data feed with Delta tables" (MS Learn, May 2026)

💧 Liquid Clustering

Liquid clustering is a flexible data layout strategy that replaces static Hive-style partitioning and manual Z-Order. You declare which columns to cluster on, and the Fabric Spark Runtime handles the physical layout automatically.

  • Clustering is a table property — you define it once; OPTIMIZE applies it
  • Regular write operations do NOT cluster the data — you must run OPTIMIZE
  • Incremental liquid clustering available in Runtime 2.0+ (no write amplification)
Data is only physically clustered when OPTIMIZE runs. Writing data to a liquid-clustered table does NOT automatically cluster it. You must schedule OPTIMIZE jobs.
Source: fabric-data-engineering.pdf — "Apply liquid clustering on Delta tables" (MS Learn)

🌊 Dataflow Gen2

What it Is

A low-code data transformation tool using the familiar Power Query interface. Over 200 connectors. Define transformations visually and output results to a lakehouse, warehouse, or other destinations.

  • Best for smaller datasets or connectors not available in other tools
  • Ideal when a data analyst (not engineer) needs to do the transformation
  • Supports scheduled refresh

Dataflow Gen2 vs. Data Pipeline — When to Choose

In Dataflow Gen2, staging for Warehouse destinations is a per-query setting: right-click the query in the Queries pane → "Enable staging". The query turns blue when staging is on. This is NOT in Options → Scale.

Dataflow Gen2 Staging Rules

  • Staging is OFF by default for Lakehouse destinations
  • Staging is REQUIRED for Warehouse destinations
  • Staging uses a Lakehouse as an intermediate buffer before loading to the target

🚚 Data Pipelines & Copy Activity

What Data Pipelines Provide

  • Scalable copy tool for large volume data movement
  • Schedule, trigger by events, or chain multiple activities
  • Copy activity, Notebook activity, Spark job activity, Dataflow activity, and more
  • Lakehouse Maintenance activity (Preview) — runs OPTIMIZE + VACUUM on schedule

Copy Activity — Staging

Staging in Copy Activity is a property of the Copy Activity itself (not of Dataflow Gen2). Staging is a separate temp storage step used when:

  • Loading to Warehouse via Copy Activity
  • Source is on-premises via SHIR (Self-hosted Integration Runtime)
Staging in pipelines (Copy Activity) ≠ Staging in Dataflow Gen2. These are separate features with different UIs. For Copy Activity: check the "Enable staging" checkbox in the Source/Sink settings. For Dataflow Gen2: right-click the query.

Pipeline Copy Activity — Fast Copy

Fast Copy uses COPY INTO for warehouse destinations, bypassing standard row-by-row insert for much higher throughput. Enabled automatically when the destination is a Warehouse and the source/format is compatible.

Lakehouse Maintenance Activity (Preview)

  • Runs OPTIMIZE (with optional V-Order) and VACUUM on Lakehouse Delta tables
  • Scheduled as part of a pipeline workflow
  • Can be chained with data loads and followed by a "Refresh SQL Endpoint" activity
Source: fabric-data-engineering.pdf — "Data pipelines", "Run Delta table maintenance in Lakehouse" (MS Learn, Feb/Apr 2026)

📥 Load to Tables (Portal)

The Lakehouse home page lets you convert CSV or Parquet files into Delta tables visually — no Spark code needed.

  • Supports: CSV and Parquet → Delta (with V-Order optimization)
  • Load into new table or append/overwrite existing table
  • Cannot define custom column schema from the UI — use a notebook for explicit column control
The Load to Tables operation is also available programmatically via the Fabric REST API (Table Load API) — useful for automation scripts.

🏢 Data Warehouse in Microsoft Fabric

Key Characteristics

  • Stores data in Delta format on OneLake (same as Lakehouse)
  • Full T-SQL surface: SELECT, INSERT, UPDATE, DELETE, MERGE, CREATE TABLE, CTAS
  • Supports multi-table ACID transactions (Lakehouse does NOT)
  • Best for SQL-first teams, BI reporting, dimensional modeling
  • RLS in Warehouse applies to ALL users including workspace Admin/Member/Contributor (unlike Lakehouse where those roles bypass RLS)
RLS in a Fabric Warehouse applies to ALL users — there is no dbo/sysadmin exemption like in SQL Server. In a Fabric Lakehouse (OneLake security), workspace Admin/Member/Contributor bypass RLS.

CTAS (CREATE TABLE AS SELECT)

-- Basic CTAS in Warehouse
CREATE TABLE dbo.sales_summary
AS
SELECT region, SUM(amount) AS total
FROM dbo.sales
GROUP BY region

-- CTAS referencing a Lakehouse table (same workspace)
-- Run from INSIDE the Warehouse
CREATE TABLE dbo.enriched_sales
AS
SELECT s.*, c.customer_name
FROM dbo.sales s
JOIN SalesLakehouse.dbo.dim_customer c ON s.customer_id = c.id
Cross-workspace CTAS is NOT supported. You can reference a Lakehouse in the same workspace using LakehouseName.dbo.table_name from inside the Warehouse, but you cannot span workspaces in a single CTAS.

Warehouse Ingestion Methods

MethodNotes
COPY INTOBulk load from files; high performance
INSERT … SELECTRow-by-row or batched insert from query
CTASCreate + populate in one statement
Pipeline Copy ActivityRequires staging for warehouse destination
Dataflow Gen2Requires staging enabled per query

Warehouse Security: DDM (Dynamic Data Masking)

  • Masks sensitive column values (e.g., showing XXXX instead of SSN)
  • Defined on specific columns in the warehouse
  • Workspace Admin, Member, Contributor automatically see unmasked data
  • Viewer role and shared users see masked data
DDM bypass: Anyone with Admin, Member, or Contributor workspace role sees unmasked data automatically. Sharing a warehouse with "Read + ReadData" grants masked access.

Direct Lake Mode

Power BI can connect to Delta tables in OneLake using Direct Lake mode — data is loaded directly from OneLake into Power BI's in-memory engine (VertiPaq) without going through a SQL endpoint.

  • Much faster than Import or DirectQuery for first query after table updates
  • Falls back to DirectQuery when certain features trigger a fallback:
ConditionResult
RLS (or a view) applied on a SQL-analytics-endpoint data source❌ Fallback to DirectQuery (slower, still works)
CLS / Object-Level Security on the SQL analytics endpoint⚠️ Corrected: NOT a fallback — returns a hard ERROR, report visuals fail to render
Frame/guardrail limit exceeded (too many rows/columns)❌ Fallback to DirectQuery (on "Direct Lake on OneLake," this errors instead of falling back)
Unsupported DAX function❌ Fallback to DirectQuery
Direct Lake mode reads from OneLake files directly. It can be used with both Lakehouse and Warehouse Delta tables as the source.
⚠️ Corrected: RLS and CLS do NOT behave the same in Direct Lake. RLS → DirectQuery fallback. CLS/OLS → hard error, no fallback. Also: this fallback behavior is specific to "Direct Lake on SQL" — "Direct Lake on OneLake" (the newer, recommended mode) doesn't support DirectQuery fallback at all; it errors instead for any of these triggers. Enforcing security via OneLake security roles instead of SQL-endpoint RLS/CLS avoids both the error and the fallback, at full in-memory speed, across every compute engine.
Source: fabric-data-engineering.pdf — "Lakehouse vs. data warehouse", "Direct Lake", Warehouse documentation (MS Learn)

🔍 SQL Analytics Endpoint — Deep Dive

Key Rules

  • Auto-provisioned alongside every Lakehouse — no separate creation needed
  • Read-only — SELECT queries only; no INSERT, UPDATE, DELETE, CREATE TABLE
  • Only surfaces Delta tables (including via shortcuts); not Files section

🛡️ RLS and CLS in Spark (OneLake Security)

How Spark Enforces OneLake Security

When a user queries a secured lakehouse table in Spark, Fabric uses a two-context execution model:

  1. User context — runs the user's notebook/Spark job with user identity; never has unfiltered access to secured tables
  2. System (security) context — privileged Microsoft-managed context that resolves RLS/CLS policies, reads raw Delta files, applies row filtering and column projection, then returns only authorized data to the user context
The system security jobs appear in Monitoring Hub as SparkSecurityControl entries — this is expected and normal. It means OneLake security is actively enforced.

Policy Behavior in Spark

Policy typeWhat Spark returns
RLS onlyAll columns, but only rows the user's RLS rule allows
CLS onlyOnly the allowed columns; all rows; SELECT * returns allowed columns only
RLS + CLS (same role)Allowed rows projected to allowed columns — supported
RLS in role A + CLS in role B (same user)❌ Query FAILS — not supported for a user in two roles with mixed policy types
Non-Delta object with rule applied❌ Access BLOCKED (RLS/CLS only on Delta Parquet)

Direct File Access is Blocked

When OneLake security is enabled on a table, non-privileged users cannot use:

# These are BLOCKED for non-privileged users
spark.read.format("delta").load("abfss://...")
DeltaTable.forPath(spark, "abfss://...")

Users must access secured tables through the lakehouse table name:

# This works — security is applied transparently
df = spark.read.table("lakehouse.secured_table")

Service Principals and RLS/CLS

RLS and CLS in Spark do NOT support service principals — only user identities are evaluated. Running notebooks with workspace identity does NOT enforce RLS/CLS for that workspace identity.

OneLake Security Roles (⚠️ renamed from "OneLake Data Access Roles" — GA, not Preview)

Configures access to specific folders, tables, rows, and columns in OneLake (more granular than workspace roles). Lets you grant read access to a subset of the data in a lakehouse without granting full workspace access. Reached General Availability around April/May 2026.

Source: fabric-data-engineering.pdf — "Spark support for OneLake security (RLS and CLS)", "Workspace roles in Lakehouse" (MS Learn, May 2026)

🌊 Streaming Data into a Lakehouse

Structured Streaming Basics

Fabric Spark supports Structured Streaming — treats live data streams as a table with new rows appended continuously. Supports Kafka, Azure Event Hubs, file sources (CSV, JSON, Parquet).

# Basic Event Hubs → Delta table streaming write
rawData = (
  df
  .withColumn("bodyAsString", f.col("body").cast("string"))
  .select(f.from_json("bodyAsString", Schema).alias("events"))
  .select("events.*")
  .writeStream
  .format("delta")                              # Write as Delta
  .option("checkpointLocation", "Files/checkpoint")
  .outputMode("append")                         # Only new rows
  .toTable("deltaeventstable")
)

Production Streaming: Spark Job Definitions

  • Use Spark job definitions (not notebooks) for production streaming
  • Configure a retry policy — automatically restarts the job when it stops unexpectedly
  • Retry policy: specify max restarts (up to infinite) and interval between retries
  • Lifetime limit: 90 days for retry policy setup
Spark notebooks are great for development/testing of streaming logic. For production, use Spark job definitions with retry policies — they are non-interactive and more robust.

Lakehouse Destination — Schema Enforcement

  • Schema is set based on the first record received
  • New writes must be schema-compatible with the existing table
  • Extra columns in incoming data are dropped
  • Missing columns write as null
  • Schema mismatch (no intersection) → schema conversion failure
Using a Lakehouse as an Eventstream destination for CDC data (database change data capture) is NOT recommended because CDC data often has schema changes that cause columns or records to be lost.

Best Approach for High-Throughput Streaming

For time-series or high-throughput scenarios, use Eventstream → Eventhouse with OneLake Availability enabled. This creates a Delta table in OneLake that a lakehouse can access through a shortcut — combining real-time KQL analytics with Delta-based SQL/Spark access.

⚡ High Concurrency Mode (Lakehouse Operations)

High concurrency mode allows multiple compatible Lakehouse operations (load, preview) to share a single Spark session instead of starting separate sessions for each.

Requirements for Session Sharing

  • Operations must be triggered by the same user
  • Operations must run in the same Lakehouse and workspace

Benefits

  • Up to 5 Lakehouse operations in one shared Spark session
  • Faster start times (subsequent ops reuse existing session)
  • Only the initiating session is billed — subsequent shared ops don't add billing
  • Especially helpful in workspaces using Managed Virtual Networks (longer startup times)
High concurrency for Lakehouse load/preview is automatic — no per-operation toggle needed. High concurrency for notebooks and pipelines requires explicit configuration in workspace settings.

Intelligent Cache

  • Automatically caches each file read within allocated cache storage on each Spark node (SSD)
  • Enabled by default for all Spark pools with 50% cache size
  • Cache is per-node — multiple executors on the same node share one cache
  • Automatically evicts LRU (least recently used) files when full
You don't benefit from intelligent cache if: (1) the file exceeds cache size, or (2) workload requires large amounts of shuffle (in that case, disable cache to free up SSD).

🔁 Deployment Pipelines & Lifecycle Management

What Deployment Pipelines Do

Deployment pipelines let you promote Fabric items (lakehouses, warehouses, notebooks, datasets, reports) across environments (Dev → Test → Prod). They are the CI/CD mechanism for Fabric items.

What Gets Copied When You Deploy

✅ IS Copied / Deployed

  • Lakehouse structure (Tables and Files definitions)
  • Notebook code
  • Pipeline definitions
  • Dataflow Gen2 definitions
  • Report layouts
  • Semantic model schema
  • Warehouse schema (tables, views, stored procedures)

❌ NOT Copied / Deployed

  • Credentials — must be reconfigured in each environment
  • Role assignments — security must be set up in target environment
  • Refresh schedules — must be reconfigured
  • Query caching settings
  • Endorsement (Certified / Promoted status)
  • App content (published apps)
  • Item IDs and URLs (change per deployment)
  • OneLake shortcuts — definitions are copied but target paths may differ
Credentials, role assignments, refresh schedules, query caching, and endorsement are never copied by deployment pipelines. You must manually configure these in each environment after deployment.

Lakehouse-Specific Deployment Pipeline Behavior

  • SQL analytics endpoints and semantic models are provisioned as part of the lakehouse — no separate deployment step needed
  • OneLake shortcut definitions are stored in the lakehouse item and are copied — but the target paths may need to be updated in the new environment
  • Actual data in the lakehouse is NOT copied — deployment copies structure/definitions, not data

Git Integration

  • Fabric items can be connected to a Git repo (Azure DevOps or GitHub)
  • Supports branch-based development workflow
  • Items are serialized to JSON/YAML in the repo
  • Git integration is used for CI (source control); deployment pipelines are used for CD (promotion)
Deployment pipelines vs. Git integration: Use Git for version control and collaboration (CI). Use deployment pipelines to promote tested code from Dev → Test → Prod (CD).
