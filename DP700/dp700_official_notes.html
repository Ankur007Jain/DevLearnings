Lakehouse Overview

What is a Lakehouse?

A Fabric Lakehouse is a data architecture platform for storing, managing and analyzing structured and unstructured data in a single location. It combines the flexibility of a data lake with the analytical power of a data warehouse.

  • All data stored in Delta format (Parquet + transaction log)
  • Two views: Lake view (Files + Tables) and SQL analytics endpoint view
  • Supports both Apache Spark (notebooks, Spark Job Definitions) and T-SQL (via SQL analytics endpoint)
  • Data stored in OneLake — one logical data lake per tenant

Lakehouse does NOT support multi-table ACID transactions. That requires a Warehouse.

Lakehouse Items

ComponentPurpose
Tables folderManaged Delta tables, auto-registered in metastore
Files folderRaw unmanaged files (any format)
SQL analytics endpointRead-only T-SQL access to Delta tables
Default semantic modelAuto-generated Power BI semantic model
Source: Lakehouse overview — Microsoft Learn

SQL Analytics Endpoint

Each Lakehouse automatically provisions a SQL analytics endpoint — a read-only T-SQL interface over the Delta tables in the Lakehouse.

What you CAN do at the SQL analytics endpoint:

  • Query Delta tables with T-SQL (SELECT)
  • CREATE VIEW, CREATE INLINE TVF, CREATE PROCEDURE
  • CREATE SCHEMA, CREATE FUNCTION, CREATE SECURITY POLICY
  • Manage permissions (GRANT, DENY, REVOKE)

What you CANNOT do:

  • CREATE TABLE (tables come from the Lakehouse, not T-SQL)
  • DML: INSERT, UPDATE, DELETE, MERGE
  • No DDL for tables (read-only data path)

SQL analytics endpoint is read-only for data. You can CREATE SCHEMA, CREATE FUNCTION, CREATE SECURITY POLICY — but NOT CREATE TABLE. For table creation use Spark or the Lakehouse interface.

Source: SQL analytics endpoint — Microsoft Learn

OneLake Shortcuts

Shortcuts are embedded pointers to storage locations inside or outside OneLake. They appear as folders in a Lakehouse or KQL database but data stays in the source.

Supported shortcut sources:

  • Internal: OneLake (other Fabric items)
  • External: Azure Data Lake Storage Gen2 (ADLS Gen2)
  • External: Amazon S3
  • External: Google Cloud Storage (GCS)
  • External: Amazon S3-compatible storage
  • External: Dataverse
  • External: On-premises data gateway (OPDG)

Shortcut Caching

Caching temporarily stores external shortcut data in OneLake for faster access.

Caching is supported ONLY for: GCS, S3, S3-compatible, and OPDG shortcuts. It is NOT supported for Azure Blob Storage or ADLS Gen2 shortcuts.

Shortcut Limitations:

  • Shortcuts cannot point to another shortcut (no chaining)
  • Shortcuts in a Lakehouse Tables folder must point to Delta tables
  • Cross-region shortcuts not supported for OneLake security roles
Source: OneLake shortcuts — Microsoft Learn

Delta Table Maintenance (OPTIMIZE & VACUUM)

OPTIMIZE

Compacts small Parquet files into larger, more efficient files. Two variants:

  • OPTIMIZE tablename — basic compaction
  • OPTIMIZE tablename VORDER — apply V-Order during compaction
  • OPTIMIZE tablename WHERE predicate ZORDER BY (col) VORDER — filter + ZORDER + V-Order

V-Order (Critical Exam Topic)

V-Order is a Fabric-specific write optimization that applies sorting, row-group elimination, and dictionary encoding to Parquet files for faster Power BI reads.

V-Order is DISABLED by default in new Fabric workspaces (spark.sql.parquet.vorder.default=false). You must explicitly enable it. This is the opposite of what some prep materials claim.

Enable V-Order: SET spark.sql.parquet.vorder.default=TRUE

V-Order can be combined with ZORDER: OPTIMIZE tablename ZORDER BY (col) VORDER

VACUUM

Removes old Parquet files no longer referenced by the Delta transaction log.

  • Default retention: 7 days
  • You cannot VACUUM below 7 days unless explicitly overriding the safety check
  • VACUUM prevents time travel beyond the retention period

Running VACUUM with retention below 7 days risks breaking concurrent readers. The default is 7 days — do not set it lower in production.

Source: Delta table maintenance — Microsoft Learn

Fabric Data Warehouse Overview

Fabric Data Warehouse is an enterprise-scale relational warehouse built on a data lake foundation. Unlike traditional warehouses, it stores data in Delta tables (Parquet + transaction log in OneLake).

Key Characteristics:

  • Full multi-table ACID transaction support ✅ (unlike Lakehouse)
  • Primarily developed with T-SQL
  • Supports DDL + DML (CREATE TABLE, INSERT, UPDATE, DELETE, MERGE)
  • Materialized views, functions, stored procedures
  • Data automatically replicated to OneLake Files for external access
  • Autonomous workload management — no knobs to tune
  • Scale near-instantaneously (storage and compute separated)

Warehouse vs. Lakehouse SQL Endpoint:

FeatureWarehouseSQL Analytics Endpoint
CREATE TABLE✅ Yes❌ No
DML (INSERT/UPDATE/DELETE)✅ Yes❌ No
Multi-table ACID✅ Yes❌ No
Stored Procedures✅ Yes✅ Yes
CREATE VIEW / TVF✅ Yes✅ Yes
CREATE SECURITY POLICY✅ Yes✅ Yes

Ingestion Methods:

  • COPY INTO (bulk load from Azure storage) — primary ingestion
  • Pipelines (Copy activity, Dataflow Gen2)
  • Cross-database ingestion: CTAS, INSERT...SELECT, SELECT INTO
  • Spark (data written directly to Delta tables)
Source: Fabric Data Warehouse overview — Microsoft Learn

Row-Level Security (RLS)

RLS restricts which rows users can see, implemented via security policies + inline table-valued functions (TVFs).

Implementation Steps:

-- 1. Create schema and TVF (filter function)
CREATE SCHEMA Security;
GO
CREATE FUNCTION Security.tvf_securitypredicate(@SalesRep AS nvarchar(50))
    RETURNS TABLE WITH SCHEMABINDING AS
    RETURN SELECT 1 AS result
    WHERE @SalesRep = USER_NAME() OR USER_NAME() = 'manager@contoso.com';
GO

-- 2. Create security policy
CREATE SECURITY POLICY SalesFilter
ADD FILTER PREDICATE Security.tvf_securitypredicate(SalesRep)
ON sales.Orders
WITH (STATE = ON);

Key Behaviors:

  • Filter predicates affect: SELECT, DELETE, UPDATE (users cannot see/delete/update filtered rows)
  • Users CAN INSERT rows that will later be filtered
  • To modify the TVF: you must DROP the security policy first, then ALTER, then recreate
  • SCHEMABINDING = ON (default) — bypasses additional permission checks on referenced objects

In Fabric (unlike SQL Server), dbo users and db_owner members ARE filtered by RLS. Security policies apply to ALL users. If admins need to see all rows, the policy must explicitly allow it.

⚠️ More precise than "Direct Lake falls back to DirectQuery" (corrected/refined, 2026-09-06): this is true specifically for "Direct Lake on SQL endpoints." If a query hits a SQL-analytics-endpoint table with RLS (or a view) enabled, Direct Lake on SQL falls back to DirectQuery. But "Direct Lake on OneLake" does NOT support DirectQuery fallback at all — if it would need to fall back, it instead returns an error (report visuals fail to render). The way to get RLS with no fallback and no error, at full Direct Lake in-memory speed, across every compute engine (lakehouse, warehouse, semantic model) — is to define the RLS in OneLake security instead of SQL-endpoint RLS. Microsoft's own guidance: "If you must enforce data-access rules, do so in OneLake security so that the rules apply across all compute engines... achieve high query performance from the in-memory cache."

RLS applies to:

  • ✅ Warehouse
  • ✅ SQL analytics endpoint (shared warehouse or lakehouse)
  • ✅ OneLake security (row-level, engine-agnostic — preferred for Direct Lake performance)
Source: Row-level security — Microsoft Learn · Direct Lake security integration — Microsoft Learn

Column-Level Security (CLS)

CLS restricts which columns users can access using the GRANT T-SQL statement.

Implementation:

-- Grant access to specific columns only (excludes CreditCard)
GRANT SELECT ON Customers(CustomerID, FirstName, LastName, Phone, Email)
TO [Charlie@contoso.com];

Queries including restricted columns will fail with an error:

Msg 230, Level 14, State 1, Line 12
The SELECT permission was denied on the column 'CreditCard'...

Key Points:

  • Implemented with GRANT (column-level), not CREATE SECURITY POLICY
  • Simpler than creating views to filter columns
  • Applies to shared warehouse or lakehouse SQL endpoint
  • Only Microsoft Entra authentication supported (no SQL auth)

⚠️ Corrected (2026-09-06) — this is NOT the same as RLS: When Direct Lake on SQL hits a table/column restricted by SQL analytics endpoint CLS (or object-level security), it does NOT fall back to DirectQuery — it returns an error and the report visual fails to render. Fallback-to-DirectQuery is specifically an RLS/view behavior; CLS/OLS is hard-error behavior. As with RLS, defining the restriction in OneLake security instead avoids both the error and any fallback, at full Direct Lake speed.

Source: Column-level security — Microsoft Learn · Direct Lake security integration — Microsoft Learn

Dynamic Data Masking (DDM)

DDM hides sensitive data from non-privileged users in query results, without changing the underlying data.

Masking Types:

TypeFunctionExample Output
DefaultMASKED WITH (FUNCTION = 'default()')Strings → XXXX, Numbers → 0, Dates → 1900-01-01
EmailMASKED WITH (FUNCTION = 'email()')aXXX@XXXX.com (first letter + .com)
RandomMASKED WITH (FUNCTION = 'random(1, 100)')Random number in range
Custom StringMASKED WITH (FUNCTION = 'partial(1,"XXX",0)')First char + XXX (prefix, padding, suffix)

Who Sees Unmasked Data:

  • Admin, Member, Contributor workspace roles have CONTROL — see unmasked data
  • UNMASK permission must be explicitly granted to others: GRANT UNMASK ON dbo.Customers TO [user]

DDM does NOT encrypt data — it only hides it in query results. Admins/Members/Contributors with CONTROL permission always see unmasked data regardless of masking settings.

Source: Dynamic data masking — Microsoft Learn

Query Insights

Query Insights provides historical query data and actionable insights for 30 days in Warehouse and SQL analytics endpoint.

Five queryinsights Views:

ViewPurpose
queryinsights.exec_requests_historyEach completed SQL request/query (last 30 days)
queryinsights.exec_sessions_historyCompleted sessions
queryinsights.long_running_queriesQueries ranked by execution time
queryinsights.frequently_run_queriesFrequently run queries (aggregated by query shape/hash)
queryinsights.sql_pool_insightsPool-level metrics, pressure indicators, resource allocation

There are 5 views in queryinsights, not 4. The 5th view (sql_pool_insights) covers pool-level metrics and pressure — commonly missed.

Key Behaviors:

  • Data retention: 30 days
  • System queries are NOT stored (user queries only)
  • Full query text visible to Admin, Member, Contributor roles
  • Queries can take up to 15 minutes to appear after completion
  • Similar queries grouped by query hash (same shape = same hash regardless of predicates)

COPY INTO Statement

COPY INTO is the primary bulk ingestion mechanism for Fabric Data Warehouse, loading data directly from Azure storage.

Basic Syntax:

COPY INTO dbo.TargetTable
FROM 'https://storageaccount.blob.core.windows.net/container/path'
WITH (
    FILE_TYPE = 'PARQUET',
    CREDENTIAL = (IDENTITY = 'Managed Identity')
);

Supported File Types:

  • CSV, Parquet, ORC
  • Source: Azure Blob Storage, ADLS Gen2

COPY INTO is for Warehouse. For Lakehouse, use Spark (notebooks/Spark Job Definitions) or COPY INTO via pipelines targeting the underlying Delta tables.

Dataflow Gen2 Overview

Dataflow Gen2 is a cloud-based, low-code/no-code data preparation tool using the Power Query experience. It ingests, transforms, and loads data from hundreds of sources into multiple destinations.

Key Improvements over Gen1:

FeatureGen2Gen1
Multiple output destinations✅❌
AutoSave & background publishing✅❌
Works with Pipelines✅❌
High-performance computing✅❌
Better monitoring✅❌
DirectQuery via dataflow connector❌✅

Supported Data Destinations:

  • Azure SQL databases
  • Azure Data Explorer (Kusto)
  • Azure Data Lake Gen2 (preview)
  • Fabric Lakehouse Tables
  • Fabric Lakehouse Files (preview)
  • Fabric Warehouse
  • Fabric KQL database
  • Fabric SQL database
  • SharePoint Files

When loading to Warehouse, staging is required. Ensure staging is enabled for all queries that load into the warehouse. Only same-workspace warehouse loading is currently supported.

Update Methods:

  • Replace: Data dropped and replaced on each refresh (default for new tables)
  • Append: New data appended to existing table on each refresh

KQL databases and Azure Data Explorer do NOT support Replace as an update method — only Append is supported for these destinations.

Automatic vs. Manual Settings (new tables):

  • Automatic (default): Managed mapping, Replace method, table dropped and recreated on refresh
  • Manual: Full control over column mapping and update method
  • Automatic settings only supported for: Lakehouse and Azure SQL database destinations

Staging:

  • Staging is ON by default (uses internal Lakehouse)
  • Disabled by default when loading to Lakehouse (for performance)
  • Required and cannot be disabled for Warehouse destination
Source: Dataflow Gen2 overview — Microsoft Learn | Destinations — Microsoft Learn

Copy Activity

The Copy activity in a Pipeline moves data between supported sources and destinations. It handles serialization/deserialization, compression, column mapping, and type conversions.

Copy Activity vs. Copy Job:

  • These are SOURCE-side parallelism settings (physical/logical/dynamic range partitions)

There is NO "Enable partitions" option on the Destination tab of a Copy activity. Partitioned output (like writing partitioned files) is done via Spark notebooks using partitionBy(), not Copy activity destination settings.

Pipeline Runs & Scheduling

Three Ways to Start a Pipeline:

  1. On-demand — Click Run in the pipeline editor
  2. Scheduled — Set time-based schedule (requires start AND end date)
  3. Event-based — Trigger on file events, job events, workspace events (uses Data Activator/Reflex)

Scheduling Options:

  • Fixed schedule — hourly, daily, weekly, monthly with specific times
  • Interval-based schedule (preview) — fixed non-overlapping windows; adds Window start time and Window end time as pipeline trigger parameters
  • Up to 20 schedules per pipeline

A scheduled pipeline MUST have both a start AND an end date — there is no "open-ended" option. For long-running pipelines, set end date to a far future date (e.g. 01/01/2099).

Failure Notifications:

  • Can be configured for scheduled runs only (not on-demand runs)
  • Set in Schedule → Failure notifications → add users/groups

Event Triggers:

  • Powered by Data Activator (Reflex) + Eventstream
  • Supports: OneLake events, Azure Blob Storage events, file created/deleted
  • Filter by folder name, file name, file type, container
  • Trigger parameters: @pipeline()?.TriggerEvent?.FileName
Source: Pipeline runs — Microsoft Learn

Self-Hosted Integration Runtime (SHIR)

SHIR enables Fabric pipelines to connect to on-premises or private network data sources that are not publicly accessible.

Key Points:

  • Installed on a machine within your private network
  • Allows Copy activity to read from on-premises SQL Server, Oracle, SAP, file shares, etc.
  • Also called on-premises data gateway in some Fabric contexts
  • SHIR is different from Managed Private Endpoints (Spark-based VNet)

A single Copy activity can only use ONE gateway. If both source and sink are on-premises with different gateways, use an intermediate cloud storage as a staging area.

Eventhouse Overview

An Eventhouse is a container that holds one or more KQL databases. It is the preferred engine for real-time, time-series, semi-structured (JSON/XML), and free-text analysis in Fabric.

Key Characteristics:

  • Designed for streaming data — query billions of events in seconds
  • One Eventhouse can host multiple KQL databases
  • Databases share capacity and resources within the Eventhouse
  • Unified monitoring and management across all databases
  • Supports structured, semi-structured (JSON, XML), and unstructured data
  • Auto-indexed by ingestion time for fast searching

Use Cases:

  • Telemetry and log data
  • Time series and IoT data
  • Security and compliance logs
  • Financial records

Ingestion Sources:

  • Eventstream (primary)
  • SDKs, Kafka, Logstash
  • Dataflows, Pipelines

Sharing:

  • Sharing an Eventhouse link gives recipient same permissions to all KQL databases, tables, dashboards, functions, materialized views within it
  • Individual KQL databases can be shared independently
Source: Eventhouse overview — Microsoft Learn

Fabric Activator (Data Activator)

Activator is a no-code event detection engine that monitors data streams and automatically triggers actions when specific patterns or conditions are detected.

Core Architecture Components:

ComponentDescription
Event sourcesEventstream, Power BI reports, Fabric/Azure events, Real-Time dashboards
ObjectsBusiness entities being monitored (e.g. freezer, vehicle, campaign). Grouped by object ID column.
PropertiesSpecific attributes of objects to monitor (e.g. temperature, balance)
RulesConditions evaluated continuously — stateless or stateful
ActionsWhat happens when rule fires

Supported Actions:

  • Fabric: Pipelines, Notebooks, Spark Job Definitions, Dataflows, User Data Functions (preview)
  • External: Power Automate flows
  • Notifications: Teams messages (individual/group/channel), Email

Rule Types:

  • Stateless: Evaluate each event in isolation (e.g. value < 50). Near-millisecond latency.
  • Stateful: Track changes over time (BECOMES, DECREASES, INCREASES, EXIT RANGE, heartbeat)

Billing:

  • Pay-as-you-go — only charged when rules are actively running
  • Activators are capacity-bound

Key Integration Points:

ComponentInteraction
EventstreamPrimary data source; alert creation embedded in Eventstream UI
Power BIEvent source for report visuals; also consumes pipeline/notebook outputs
PipelineTarget of Activator rule triggers

Sensitivity Labels

Sensitivity labels (from Microsoft Purview Information Protection) classify and protect Fabric content based on data sensitivity.

Key Points:

  • Applied to Fabric items (lakehouses, warehouses, reports, semantic models, etc.)
  • Labels flow downstream — when you apply a label to a dataset, it can propagate to dependent items
  • Labels appear in the Fabric UI and in data exports
  • Labels with protection can encrypt files and apply permissions

Sensitivity Labels in Deployment Pipelines:

Sensitivity labels are NOT automatically copied during deployment in most cases. Labels ARE copied only when: (1) a new item is deployed (clean deploy), OR (2) the source item has a protected label and the target does not.

Also NOT copied during Deployment Pipeline:

  • Data (only metadata is copied)
  • Permissions / URL / ID
  • Refresh schedule
  • Data source credentials
  • Role assignment
  • Endorsement settings
  • App content and settings
Source: Sensitivity labels overview — Microsoft Learn

Deployment Pipelines

Deployment pipelines provide an ALM (Application Lifecycle Management) tool for managing content across Dev → Test → Production stages.

Key Characteristics:

  • 2–10 stages per pipeline (default: 3)
  • Stages are permanent after creation (cannot rename/delete stages)
  • Deploy content from any adjacent stage in either direction
  • Maximum 300 items per single deployment

Item Pairing:

  • Items in adjacent stages are "paired" by connection (not by name)
  • Paired items can have different names across stages
  • Items with same name/type but not paired create a DUPLICATE (don't overwrite)
  • Deployment overwrites the paired item's content but preserves its ID, URL, and permissions

Properties Copied During Deployment:

  • ✅ Data sources, Parameters, Report visuals, Report pages, Dashboard tiles, Model metadata, Item relationships
  • ✅ Sensitivity labels (only under specific conditions — see above)

Properties NOT Copied (Critical Exam List):

Not CopiedExplanation
DataOnly metadata copied; run refresh after deployment
URL / ID / PermissionsEach stage has its own identity
Refresh scheduleMust be reconfigured per stage
Data source credentialsMust be reconfigured per stage
Endorsement settingsNot propagated across stages
Role assignmentNot copied
Workspace settingsEach stage has own workspace
App content and settingsMust be manually updated

After deploying a semantic model with a Direct Lake connection, the model in the target stage still points to the source stage lakehouse. You must manually configure datasource rules to bind it to the target stage lakehouse.

Autobinding:

  • Deployment pipelines automatically connect (autobind) deployed items to paired items in the target stage
  • Both pipelines in cross-pipeline autobinding must have the same number of stages

Required Permissions:

  • To deploy: Pipeline admin + at least Contributor in both source and target workspaces
  • Workspace must reside on a Fabric capacity
Source: Deployment pipelines intro — Microsoft Learn | Deployment process — Microsoft Learn

Managed Private Endpoints

Managed private endpoints allow Fabric workloads to securely access private network data sources without public internet exposure.

Key Points:

  • Created by workspace admins via workspace settings
  • Microsoft Fabric creates and manages the endpoints
  • Supported for: Fabric trial capacity and all Fabric F SKU capacities
  • Require Fabric Data Engineering (Spark-based) workload in both the tenant home region and capacity region

Direct Lake Mode

Direct Lake is a Power BI semantic model storage mode that reads Delta tables directly from OneLake without importing or using DirectQuery — combining the speed of Import with the freshness of DirectQuery.

How Direct Lake Works:

  • Reads Parquet files directly from OneLake into memory (column store framing)
  • When a query comes in, the engine checks if the required data is already "framed" (cached)
  • If not framed, data is loaded from OneLake on demand
  • V-Order optimized Parquet files load significantly faster into Direct Lake

Direct Lake Fallback vs Error — ⚠️ corrected, these are NOT the same behavior

This is specifically about "Direct Lake on SQL endpoints." RLS and CLS behave differently — don't lump them together:

TriggerWhat actually happens
Row-Level Security (or a view) on the SQL analytics endpointFalls back to DirectQuery (slower, but the report still renders)
Column-Level Security / Object-Level Security on the SQL analytics endpoint❌ Does NOT fall back — returns an error, report visuals fail to render entirely
Frame/guardrail limit exceededModel exceeds the rows/columns/capacity guardrails for the SKU → falls back to DirectQuery (or errors, on Direct Lake on OneLake — see below)
Unsupported data typesSome complex types force DirectQuery

⚠️ "Direct Lake on OneLake" (the newer/recommended mode) does NOT support DirectQuery fallback at all — for any of the above triggers, it returns an error instead of degrading to DirectQuery. To get RLS/CLS/OLS enforcement with zero fallback and zero error, at full in-memory Direct Lake speed, across every compute engine — define the security in OneLake security roles (not SQL-endpoint RLS/CLS). This is Microsoft's own stated best practice.

Frame Limits by SKU:

  • Frame limits vary by capacity SKU — larger SKUs support more rows/columns in memory
  • When limits are exceeded on Direct Lake on SQL, the query falls back to DirectQuery; on Direct Lake on OneLake, it errors instead
Source: Direct Lake overview — Microsoft Learn · Direct Lake security integration — Microsoft Learn

High Concurrency Mode (Spark)

High concurrency mode lets multiple Spark workloads share one running Spark session instead of starting a new session per workload.

How It Works:

  • One Spark application hosts multiple workloads via separate REPL cores
  • Each REPL core isolates execution state (variables don't bleed between notebooks)
  • Subsequent workloads start much faster (session already running)
  • FAIR scheduling across REPL cores to reduce starvation

Session Sharing Requirements:

  • Sessions must be within a single-user boundary
  • Sessions use the same default Lakehouse configuration
  • Sessions use the same Spark compute settings

If ANY of the three requirements differ (different user, different lakehouse, different compute settings), Fabric starts a separate Spark session instead of sharing.

Billing:

  • Only the initiating notebook or pipeline activity that starts the shared Spark application is billed
  • Subsequent sessions sharing the same Spark session are NOT billed separately
  • This is reflected in Capacity Metrics — usage reported against the initiating notebook

Session Sharing Limits:

SettingValue
Default max notebooks per session5
Maximum configurable limit50
Configuration propertyspark.highConcurrency.max = <2–50>
Where to setEnvironment item → Spark Properties

Default is 5 notebooks per session. You must explicitly set spark.highConcurrency.max to increase it — it doesn't change automatically.

Speed Benefit:

  • Custom pools with high concurrency mode: session start up to 36x faster than standard Spark session

Apache Spark Compute (Starter Pools & Custom Pools)

Starter Pools:

  • Pre-warmed Spark clusters — always on and ready
  • Default startup: 5–10 seconds (no libraries, Medium node size, no special networking)
  • Only support Medium node size
  • NOT supported with Private Links or Managed VNets (falls back to 2–5 min on-demand)

Starter Pool Startup Times:

ScenarioTypical Startup
Default settings, no libraries5–10 seconds
Custom libraries / Spark properties5–10 sec + 30 sec–5 min (library setup)
High traffic in region (no libraries)2–5 minutes
Private Links / Managed VNets2–5 minutes

Selecting any node size other than Medium, or using Private Links/Managed VNets, disables Starter Pool optimization. Session start falls back to on-demand (2–5 minutes).

Custom Spark Pools:

  • Created by workspace admins (require admin permission)
  • Take ~3 minutes to start (Spark gets nodes from Azure)
  • Session expires after 20 minutes of inactivity (configurable)
  • Pool deallocated after 2 minutes of inactivity post-expiry
  • Supports Autoscale and Dynamic Allocation

Node Sizes:

X-Large and XX-Large are only available for non-trial Fabric SKUs. Node-to-executor ratio is always 1:1 in Fabric (one executor per worker node).

Billing:

  • Charged only for active session duration (not cluster idle time or provisioning)
  • Billing stops when Spark session expires
