1.2 · High Concurrency Mode vs Autoscale
▼
FeatureWhat It DoesWhen to Use
High Concurrency ModeShares ONE running Spark session across multiple workloads from the same user. Each gets its own REPL core. Eliminates cold-start wait.One user running multiple notebooks simultaneously. Reduces startup by up to 36×.
AutoscaleAutomatically adds/removes Spark nodes (executors) based on workload demand.Variable workload with unpredictable compute peaks.
🚨 Critical — Often Tested Wrong High Concurrency Mode is single-user boundary — it does NOT share sessions between different users. Default max: 5 notebooks per session. Can increase to 50 via spark.highConcurrency.max in Environment settings.
⚠️ Gotcha Session sharing requires: same user + same default Lakehouse + same Spark compute settings. If ANY differs, a separate Spark session starts.
Q: A data engineer runs 5 notebooks at once. Spark takes 3 min to start each. What to enable?
High Concurrency Mode. Shares the existing session — no new startup per notebook. NOT autoscale (that scales nodes, not sessions).

🚨 Shortcut Caching — Tested! Caching is supported ONLY for: GCS, S3, S3-compatible, and on-premises data gateway shortcuts. ADLS Gen2 shortcuts do NOT support caching.
Enable in: Workspace Settings → OneLake → toggle Cache ON → set retention (1–28 days).

⚠️ Gotcha: Shortcut location rules
In the Tables/ folder: shortcuts at top level only — no subdirectories. The target must be Delta Parquet format for the lakehouse to auto-recognize it as a table.
In the Files/ folder: shortcuts at any depth, any data format.
⚠️ Gotcha: Deleting shortcuts
Deleting a shortcut itself = only removes the shortcut object, target data is untouched.
Deleting a FILE inside a shortcut = DOES delete the file at the target (if you have write permission).
⚠️ Gotcha: KQL Database shortcuts
Shortcuts in a KQL database appear in the Shortcuts folder and are treated as external tables. Query with external_table('MyShortcut').
Q: A lakehouse in Workspace A needs to expose its Sales table to Workspace B without copying data. What's the most efficient approach?
Create an internal OneLake shortcut in Workspace B's lakehouse pointing to the Sales table in Workspace A. No data is copied. Users in B query it through the shortcut.
1.4 · Deployment Pipelines (Lifecycle Management)
▼
ℹ️ Key Facts A deployment pipeline can have 2–10 stages (default 3: Dev → Test → Production). Each stage maps to a separate Fabric workspace. A workspace can only be assigned to ONE stage.

What Gets Deployed

Definitions only — NO data in tables. Items: Lakehouses, Warehouses, Notebooks, Pipelines, Dataflows Gen2, Reports, Semantic Models, Eventhouses, KQL Databases, Eventstreams, Environments.

Key Concepts

ConceptWhat It Means

Item PairingItems in adjacent stages are "paired" — deployments overwrite the paired item. Un-paired items of the same name create duplicates instead of overwriting.
Deployment Pipelines vs Azure PipelinesFabric Deployment Pipelines = ALM for Fabric items. Azure Pipelines (ADO) = CI/CD for code. DIFFERENT products.

1.7 · Advanced Security: DDM, CLS, RLS, Sensitivity Labels
▼

Dynamic Data Masking (DDM)

Mask TypeFunctionExample
DefaultFull mask by data type (XXXX for strings, 0 for numbers, 1900-01-01 for dates)MASKED WITH (FUNCTION = 'default()')
EmailFirst letter + @XXXX.comjXXX@XXXX.com
RandomRandom number in a rangerandom(1, 100)
Custom String (partial)Show prefix, custom padding, suffixpartial(1,"XXXXXXX",0) → 5XXXXXXX
🚨 Who Sees Unmasked Data? Users with Admin, Member, or Contributor workspace role automatically have CONTROL permission on the warehouse and see UNMASKED data by default.
To allow a user without those roles to see unmasked data: grant the UNMASK permission.
DDM does NOT prevent inference attacks — a user with query access can run range queries to guess values.

Column-Level Security (CLS)

Use DENY SELECT ON table(column) TO user. The column becomes invisible/inaccessible. Applies at the SQL analytics endpoint or warehouse.

Row-Level Security (RLS)

Create an inline table-valued function filtering rows, then create a security policy binding the function to a table. Works in the SQL analytics endpoint and warehouse. Users only see rows matching the predicate.

Sensitivity Labels

  • Applied at item level (lakehouse, warehouse, report, semantic model)
  • Propagate downstream automatically — label a lakehouse table, reports built from it inherit the label
  • Labels do NOT block access on their own — they classify and can trigger policies (e.g., block export)
  • Admin configures which labels are available from Microsoft Purview / Purview Information Protection
Q: A user has Contributor role and queries a table with DDM on the Email column. What do they see?
The actual unmasked email. Contributor has CONTROL permission on the warehouse by default, which includes UNMASK rights. Only users with lower permissions (e.g., shared via item permission only) see the masked value.

2.1 · Copy Activity & Batch Ingestion
▼

Copy Activity is the workhorse of Data Pipelines. It moves data from a source to a sink with optional transformations via Mapping Data Flows.

Key Settings

SettingWhat It Controls
Degree of Copy ParallelismNumber of parallel copy threads (default varies by source). Set higher for large tables.
Partition optionSplit large tables into partitions for parallel reading (physical partitions, dynamic range, or column-based)
Write behaviorInsert / Upsert / Overwrite — controls how data lands at sink
Fault toleranceSkip incompatible rows; log skipped rows to storage

Incremental Load Pattern (Watermark)

  1. Store a watermark value (e.g., last ModifiedDate) in a control table or pipeline variable
  2. Use a Lookup activity to GET the current watermark
  3. Use Copy Activity with filter: WHERE ModifiedDate > @watermark
  4. Use a Stored Procedure / Script activity to UPDATE the watermark to MAX(ModifiedDate) from the new load
✅ Tip The watermark pattern is the most commonly tested incremental load approach. Always: Read watermark → Filter copy → Update watermark AFTER successful copy.
Q: A pipeline must load only new records since the last run. The source has a LastModified column. What pattern is correct?
Watermark pattern: store last run timestamp in a control table. Each run: (1) read watermark, (2) copy WHERE LastModified > watermark, (3) update watermark = MAX(LastModified) from current batch after success.

2.3 · Metadata-Driven Ingestion (Control Table Pattern)
▼

Used when you need to ingest many tables (e.g., 50+ source tables) without creating 50 separate Copy Activities.

Pattern

  1. Create a control table in a lakehouse/warehouse with columns: source_name, source_connection, table_name, destination_path, is_active, last_watermark
  2. Use a Lookup activity to read all rows from the control table
  3. Use a ForEach activity to iterate over each row
  4. Inside ForEach: Copy Activity parameterized with @item().source_name, @item().table_name, etc.
  5. Update watermark per table after successful copy
✅ Why This Matters on the Exam The exam tests whether you know to use a control table + ForEach rather than hardcoding many activities. If the scenario says "50 tables, scalable solution, no hardcoding" → metadata-driven ingestion.
Pipeline:
  Lookup → control_table (all active rows)
  ForEach (@activity('Lookup').output.value)
    Copy Activity (source = @item().connection, table = @item().table_name)
    Script Activity (UPDATE control_table SET watermark = ...)

2.5 · Eventstream (No-Code Streaming)
▼

Eventstream brings real-time events into Fabric, transforms them, and routes to multiple destinations — without any code.

Key Facts

  • Backed by Azure Event Hubs — Kafka protocol compatible
  • Delivery guarantee: At-least-once (not exactly-once)
  • Max message size: 1 MB
  • Max retention period: 90 days
  • Minimum recommended capacity: F4

Sources → Eventstream → Destinations

Sources (examples)Destinations

No-Code Transformations Available

🚨 Key Exam Point Eventstream can route to MULTIPLE destinations simultaneously. Each destination gets the full stream independently.
Q: Real-time IoT data needs to go to an eventhouse for KQL analysis AND a lakehouse for batch reporting — no code allowed. What tool?
Eventstream with two destinations: Eventhouse (for KQL) and Lakehouse (for Delta/batch). No code needed. Multiple destinations supported simultaneously.
2.6 · Spark Structured Streaming
▼

Code-based streaming in PySpark/Scala. Use when you need custom transformation logic that Eventstream can't express.

Key Concepts

ConceptWhat It MeansExam Trigger
CheckpointSaves progress to storage so the stream can resume after failure without reprocessing old data"resume after failure", "exactly-once", "recovery"
WatermarkTells Spark how late data can arrive before discarding it. .withWatermark("timestamp", "10 minutes")"late arriving data", "out of order events"
TriggerControls when micro-batches process. Options: default (ASAP), fixed interval, once, available-now"process every 30 seconds", "process all available data once"
Output ModesAppend (new rows only), Complete (full result table), Update (only changed rows)"write new records only", "update existing aggregations"
df_stream = spark.readStream.format("eventhub")...
df_agg = (df_stream
  .withWatermark("EventTime", "5 minutes")
  .groupBy(window("EventTime", "1 hour"), "DeviceId")
  .agg(avg("Temperature").alias("avg_temp")))

df_agg.writeStream
  .format("delta")
  .outputMode("append")
  .option("checkpointLocation", "abfss://container/checkpoint/")
  .start("Tables/DeviceAggregates")
⚠️ Checkpoint is critical. Without a checkpoint, a failed stream restarts from the beginning (reprocesses all data). Always configure checkpointLocation.

RTI Storage Types

Storage TypeHow Data Gets ThereQuery PerformanceUse When

Accelerated shortcut = eventhouse builds its own indexes on the OneLake Delta data → fast KQL queries.
Non-accelerated shortcut = no indexes → slow, use external_table('name') to query.
Q: A KQL database has a shortcut pointing to ADLS Gen2 external storage. Queries use external_table(). What storage type is this and is it fast?
Non-accelerated shortcut. It reads from the external source on each query — no KQL indexes are built. Performance is slower than native storage or accelerated shortcuts.

3.4 · OPTIMIZE, V-Order & Z-Order
▼

OPTIMIZE — Bin Compaction

Consolidates many small Parquet files into fewer larger files. Run in a Fabric notebook or Spark job definition. NOT available in SQL analytics endpoint or Warehouse SQL editor (T-SQL only there).

%%sql
-- Basic compaction
OPTIMIZE schema_name.table_name;

-- Compact + apply Z-Order on a column
OPTIMIZE schema_name.table_name WHERE date >= '2025-01-01'
ZORDER BY (customer_id);

-- Compact + apply V-Order layout
OPTIMIZE schema_name.table_name VORDER;

-- Compact + Z-Order + V-Order together
OPTIMIZE schema_name.table_name ZORDER BY (customer_id) VORDER;

V-Order vs Z-Order

V-OrderZ-Order
What it doesOptimizes internal Parquet file layout (row-group encoding, compression) for faster reads across Fabric enginesClusters related values for a specific column together in the same files, enabling data skipping for selective filters
BenefitBroad read performance improvement (dashboarding, repeated scans)Filter performance improvement for queries filtering on the Z-ordered column(s)
DefaultDisabled by default in new Fabric workspaces (spark.sql.parquet.vorder.default=false)Not applied by default — must be specified in OPTIMIZE
Write overhead~15% slower writes on averageSlower compaction (more data movement)
KeywordVORDERZORDER BY (col)
⚠️ V-Order disabled by default — V-Order was changed to be OFF by default to improve write performance for ingestion workloads. Enable it explicitly for read-heavy scenarios like dashboarding.
⚠️ After enabling V-Order via table properties, only FUTURE writes are affected. Existing Parquet files are NOT rewritten. To rewrite existing files with V-Order, run OPTIMIZE ... VORDER.
Q: Queries on a Delta table frequently filter by customer_id. What optimization would most help?
OPTIMIZE table ZORDER BY (customer_id) — Z-Order clusters rows with the same customer_id together, allowing data skipping to skip entire files when filtering by customer_id.
3.5 · VACUUM, Primary Keys & Warehouse Design
▼

VACUUM

Removes Parquet files that are no longer referenced by the Delta transaction log (unreferenced / old version files from updates/deletes).

%%sql
-- Default: retains 7 days (168 hours) of history
VACUUM schema_name.table_name;

-- Explicit retention
VACUUM schema_name.table_name RETAIN 168 HOURS;  -- 7 days
VACUUM schema_name.table_name RETAIN 336 HOURS;  -- 14 days
⚠️ VACUUM removes time travel! After running VACUUM with default 7-day retention, you cannot time-travel to versions older than 7 days. Setting shorter retention breaks time-travel capability.
⚠️ VACUUM runs in notebooks only — same as OPTIMIZE. Not available in T-SQL SQL analytics endpoint.

Primary Keys in Fabric Warehouse — NOT ENFORCED

🚨 Critical Exam Fact In Fabric Warehouse, PRIMARY KEY, UNIQUE, and FOREIGN KEY constraints are defined for documentation purposes only — they are NOT enforced. Duplicate values on a primary key column will NOT raise an error. The constraint is metadata-only.

This is because Fabric Warehouse is a distributed MPP system optimized for analytics, not OLTP.

Lakehouse vs Warehouse Decision

Use Lakehouse WhenUse Warehouse When
Storing raw/Bronze/Silver data in Delta formatGold layer, serving SQL reports to multiple users
Running Spark notebooks / PySpark transformsT-SQL stored procedures, views, complex SQL
Data scientists / engineers need full Spark accessBI analysts using SQL, Power BI Direct Lake
Schema-on-read, flexible structureSchema-on-write, structured, governed
Lower cost for raw storageDDM, CLS, RLS needed (only in warehouse)
✅ KQL Database decision trigger → "real-time", "streaming logs", "telemetry", "time-series analysis", "KQL query syntax". If the exam mentions KQL or sub-second query performance on streaming data → KQL Database in an Eventhouse.
Q: A developer defines a PRIMARY KEY on a Fabric warehouse table and inserts duplicate values. What happens?
The insert succeeds. Primary key constraints in Fabric Warehouse are NOT ENFORCED — they are metadata hints only, for documentation and query optimizer hints. No error is raised on duplicate inserts.

🖥️ Hands-On: Practice Optimization

  1. Create a Delta table in a Lakehouse with 100k+ rows
  2. Run several DELETE/UPDATE operations to generate old version files
  3. Run DESCRIBE HISTORY table — observe the version history
  4. Run OPTIMIZE table — check file count before/after
  5. Run VACUUM table RETAIN 0 HOURS (requires overriding safety check) — watch old files disappear
  6. Try time travel: SELECT * FROM table VERSION AS OF 1 — see what happens after VACUUM
