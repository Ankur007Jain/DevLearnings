🏗️ Microsoft Fabric — Architecture Overview

What is Fabric?

  • Unified analytics platform combining data engineering, data science, data warehousing, real-time analytics, and BI
  • Built on top of OneLake — a single logical data lake for the entire organization
  • All data stored in Delta Parquet format by default
  • Requires a Fabric Capacity (provides CPU/memory) — created in Azure Portal

Fabric Capacity

  • Required for everything except Power BI
  • Created in Azure Portal → Microsoft Fabric resource
  • SKUs: F2, F4, F8, F16, F32, F64, F128, F256, F512, F1024, F2048
  • Pause/Resume from: Azure Portal → Microsoft Fabric (not from Fabric workspace)
  • Trial: 60 days, requires work/school email
⚠️ Exam trap: You pause Fabric capacity from Azure Portal → Microsoft Fabric, not from inside the Fabric workspace itself.

Workspaces

  • Must be assigned to a Fabric capacity (or Trial capacity) to use Fabric features
  • Roles: Admin, Member, Contributor, Viewer
  • Min to run notebook: Contributor
  • Min to VIEW notebook outputs: Viewer
  • Min to compare deployment pipeline stages: Contributor + pipeline admin
  • Assigning workspace to pipeline stage requires: Workspace Admin

Fabric Item Types

Data stores:
  • Lakehouse — Delta tables + Files
  • Warehouse — T-SQL only, full DW
  • Eventhouse — KQL databases
  • KQL Database — time-series analytics
Compute/ETL:
  • Notebook — PySpark/SQL/Scala
  • Dataflow Gen2 — Power Query no-code
  • Data Pipeline — orchestration
  • Spark Job Definition — standalone Spark
  • Eventstream — real-time streaming

OneLake

  • Single data lake for entire organization — one per tenant
  • All lakehouses and warehouses store data here automatically
  • Accessible via OneLake File Explorer app on Windows
  • Shortcuts allow accessing external data without copying it

🔄 Dataflow Gen2 — Core Concepts

Creating a Dataflow Gen2

  • Workspace → New → Dataflow Gen2
  • From Lakehouse → Get Data → New Dataflow Gen2
  • Uses Power Query interface
  • If Git connected: Save and Run (no Publish button)

Data Destinations (where data goes)

  • ✅ Lakehouse (Tables)
  • ✅ Warehouse
  • ✅ Azure SQL Database
  • ✅ Azure Data Explorer / Eventhouse
  • ✅ Azure Blob Storage
  • ❌ Dataverse — NOT a destination (only a source)
⚠️ Exam trap: Dataverse is available as a SOURCE but NOT as a destination in Dataflow Gen2.

Scheduling

  • Minimum frequency: 30 minutes
  • Access: Home → Schedule, or workspace ⋯ → Schedule
  • Can set start/end dates and times
⚠️ Exam trap: Dataflow Gen2 minimum schedule = 30 minutes. Pipelines minimum = 1 minute.

Fast Copy

  • Improves throughput for supported connectors (Azure SQL, etc.)
  • Enable via: Home → Options → Scale tab → "Allow use of fast copy connectors"
  • Uses staging internally
⚠️ Path to Fast Copy: Home → Options → Scale tab. NOT Transform tab, NOT right-click.

Incremental Refresh

  • Access: Right-click on the query → Incremental refresh
  • Loads only new/changed data based on date/time range
⚠️ Path to Incremental Refresh: Right-click on the query — NOT Home → Options.

Monitoring

  • Refresh history: Home → Refresh History
  • Shows each refresh run, status, duration, rows loaded

Transformations in Dataflow Gen2

  • Remove columns: Home → Remove Columns
  • Remove rows: Home → Remove Rows → Remove Errors / Remove Duplicates / Remove Blank Rows
  • Change type: click column header type icon, or Transform → Data Type
  • Replace values: Transform → Replace Values
  • Split column: Transform → Split Column
  • Group By: Transform → Group By

Merge Queries (Joins)

  • Inner join — only matching rows from both tables
  • Left outer — all rows from left + matching from right (nulls for no match)
  • Right outer — all rows from right + matching from left
  • Full outer — all rows from both (nulls where no match)
  • Left anti — rows in left that have NO match in right
  • Right anti — rows in right that have NO match in left
  • Merge Queries as New — creates a third query without modifying originals

Identifying Missing Data

  • Null values appear in merged results where no match found
  • Use Right outer or Full outer to see unmatched rows
  • Remove Errors: Home → Remove Rows → Remove Errors
  • Duplicate a query: keep errors in one copy, remove in another

⚙️ Data Pipelines — Activities & Configuration

Common Pipeline Activities

  • Copy Data (Copy Activity)
  • Dataflow (runs a Dataflow Gen2)
  • Notebook
  • Stored Procedure
  • For Each (loop)
  • If Condition (branching)
  • Wait
  • Lookup
  • Delete Data

Copy Activity — Tab Reference

  • General tab — Name, Description, Timeout (default 12h), Retry count, Retry interval
  • Source tab — Connection, table/query/stored proc, partition options
  • Destination tab — Connection, table, write method, Enable partitions (for file partitioning)
  • Settings tab — Enable staging (for COPY INTO), logging, data consistency
⚠️ Timeout/Retry: General tab. Staging: Settings tab. File partitioning: Destination tab → Enable partitions.

Copy Tool vs Copy Activity

  • Copy tool (assistant) — can select multiple tables at once, wizard-driven
  • Copy Activity — one table per activity (but can reconfigure), more control
  • COPY INTO: only from Azure Storage Account (not from other sources)

Scheduling Pipelines

  • Minimum frequency: 1 minute
  • Access: Home → Schedule, or Run → Schedule
  • Also: workspace ⋯ → Schedule
  • Options: Minutely, Hourly, Daily, Weekly, Monthly

Incremental Load Pipeline Pattern

✅ Correct pattern: Lookup (current watermark) → Lookup (max watermark from source) → Copy Data (WHERE timestamp > watermark) → Stored Procedure (update watermark)
⚠️ Exam trap: There is NO Delete activity in an incremental load pipeline. The watermark table is updated by a Stored Procedure, not a Delete activity.

Monitoring Pipeline Runs

  • Run → View Run History — shows each activity status
  • Status icons: Queued → In Progress → Succeeded / Failed
  • Click a run to see per-activity details and durations
  • Monitor hub in workspace also shows all pipeline runs

Pipeline Parameters

  • Add parameters in Pipeline canvas → Parameters tab (bottom)
  • Pass to Notebook activity: Settings tab → Base parameters
  • Dynamic content: use @pipeline().parameters.paramName syntax
⚠️ Notebook parameters in pipeline: Settings tab → Base parameters (NOT General tab).

📓 Notebooks — PySpark, SQL & Automation

Reading Data

# Read from Files section df = spark.read.format('csv').option('header','true').load('Files/folder/file.csv') df = spark.read.format('parquet').load('Files/folder/') df = spark.read.format('delta').load('Tables/tablename') # Read as streaming (Auto Loader) df = spark.readStream.format('cloudFiles').option('cloudFiles.format','parquet').load('Files/folder/') # OR stream from Delta table df = spark.readStream.format('delta').load('Tables/tablename')
⚠️ Streaming read: Use spark.readStream with cloudFiles for continuously arriving files. spark.read is batch (one-time).

Writing Data

# Write to Delta table (overwrite) df.write.format('delta').mode('overwrite').saveAsTable('tablename') # Append to existing table df.write.format('delta').mode('append').saveAsTable('tablename') # Write to Files section df.write.format('parquet').save('Files/output/') # Write streaming df.writeStream.format('delta').outputMode('append').option('checkpointLocation','Files/checkpoint/').start('Tables/tablename')

DataFrame Operations

# Select columns df.select('col1', 'col2') df[['col1', 'col2']] # Filter rows df.filter(df['col'] > 100) df.where(df['status'] == 'Active') # Add column df.withColumn('new_col', df['price'] * df['qty']) # Cast data type df.withColumn('col', df['col'].cast('integer')) # Group and aggregate df.groupBy('category').agg({'sales': 'sum', 'qty': 'avg'}) # Sort df.orderBy('date', ascending=False) # Handle nulls df.dropna() # drop rows with any null df.dropna(subset=['col1']) # drop rows where col1 is null df.fillna(0) # replace nulls with 0 df.fillna({'col1': 0, 'col2': 'Unknown'}) # Join df1.join(df2, on='key', how='inner') # inner, left, right, outer

Using SQL in Notebooks

# Run SQL magic %%sql SELECT category, SUM(sales) as total FROM tablename GROUP BY category ORDER BY total DESC # Or via spark.sql() result = spark.sql("SELECT * FROM tablename WHERE year = 2026")

Scheduling Notebooks

  • Run → Schedule (same pane as pipelines and dataflows)
  • Can schedule by minute, hourly, daily, weekly
  • View runs: Run → View Recent Runs

Notebook in Pipeline

  • Add Notebook activity to pipeline
  • Pass parameters: Settings tab → Base parameters
  • In notebook: use mssparkutils.notebook.getParam('paramName')

High Concurrency Mode

  • Same Spark session shared by multiple notebooks simultaneously
  • 36x faster session start vs standard
  • Enable: Workspace Settings → Data Engineering/Science → Spark settings → High Concurrency tab
⚠️ High Concurrency location: Workspace Settings → Data Engineering/Science tab → Spark settings.

Spark Structured Streaming in Notebooks

# Read streaming data df = spark.readStream.format('delta').load('Tables/events') # Write with checkpoint df.writeStream \ .format('delta') \ .outputMode('append') \ .option('checkpointLocation', 'Files/checkpoints/events') \ .start('Tables/processed_events')

Spark Job Definition

  • Runs a standalone Python/Scala/R Spark script (not interactive notebook)
  • Upload .py file as the main definition file
  • Good for production batch jobs
  • Uses spark.readStream for streaming from a folder of files

🏠 Lakehouse — Structure, Shortcuts & Optimization

Lakehouse Structure

  • Tables/ — managed Delta tables, auto-discovered schema, queryable via SQL endpoint
  • Files/ — raw files (CSV, Parquet, JSON, etc.), not auto-queried by SQL
  • SQL analytics endpoint: READ ONLY — cannot CREATE, INSERT, UPDATE, DELETE
⚠️ SQL endpoint is READ ONLY. To write/create tables use Spark notebooks or Dataflow Gen2. Only Warehouse supports full T-SQL write operations.

Shortcuts

  • Create: Files folder → New shortcut (or Tables → New shortcut)
  • Sources: ADLS Gen2, Amazon S3, Google Cloud Storage, OneLake, S3-compatible, On-premises Data Gateway
  • No data is copied — shortcut reads data in-place from external source
  • ADLS Gen2 shortcuts: data stays in Azure, Fabric reads it directly

Shortcut Caching

  • Reduces egress charges from external cloud reads
  • Enable: Workspace Settings → OneLake → Cache for shortcuts
  • ✅ Supported: Amazon S3, Google Cloud Storage (GCS), S3-compatible, On-premises Data Gateway
  • ❌ NOT supported: ADLS Gen2, Fabric Lakehouse shortcuts (already on Azure)
  • Files > 1GB are NOT cached
  • If external file changes: new version is read, cache updated
⚠️ Shortcut caching: Works for S3, GCS, S3-compatible — NOT for ADLS Gen2 or other Fabric items. This is a frequent exam trap.

File Partitioning

  • Splits output files by column value (e.g., year, country)
  • Implemented via: Pipeline → Copy Activity → Destination tab → Enable partitions → select column
  • Creates folder structure: Files/tablename/year=2024/month=01/
  • Improves query performance via partition pruning
⚠️ File partitioning path: Pipeline Copy Activity → Destination tab → Enable partitions.

Delta Table Optimization

  • OPTIMIZE — compacts many small Parquet files into larger ones (~128MB target). Fixes "small files problem" from streaming writes.
  • VACUUM — removes old/deleted files after retention period (default 7 days). Run after OPTIMIZE.
  • V-Order — write-time sorting/encoding optimization
    • ✅ Improves read speed 10–50% (Power BI DirectLake, SQL, Spark)
    • ❌ Decreases write speed ~15%
    • ON by default in Fabric
  • ZORDER — sorts data within files by column for predicate pushdown: OPTIMIZE table ZORDER BY (col)
⚠️ OPTIMIZE vs VACUUM: OPTIMIZE = compact files. VACUUM = delete old files. V-Order = improves reads, hurts writes slightly.
-- Run OPTIMIZE on Delta table OPTIMIZE delta.`/path/to/table` -- or from Lakehouse: right-click table → Maintenance → OPTIMIZE -- Run VACUUM (removes files older than retention period) VACUUM delta.`/path/to/table` RETAIN 168 HOURS -- 7 days default -- OPTIMIZE with ZORDER for query column OPTIMIZE tablename ZORDER BY (OrderDate, Region)

Delta Lake Copy-on-Write

  • UPDATE/DELETE writes new Parquet files for changed rows
  • Old files marked as tombstoned in transaction log
  • Old files REMAIN on disk until VACUUM runs
  • This is why storage grows after UPDATE — expected behavior

OneLake Data Access Roles (OLDAR)

  • Path-based access control within a lakehouse
  • Enable: Lakehouse → Manage → Security (OneLake Data Access)
  • Create roles with folder-level path rules (e.g., Files/raw/ or Tables/sales/)
  • Assign users/security groups to roles
  • More granular than workspace roles (which apply to all items)

Lakehouse Access Permissions

  • Read — can connect to SQL analytics endpoint
  • ReadAll (OneLake) — can read ALL Delta files via Spark/OneLake (needed for PySpark)
  • No workspace role needed for item-level permissions (share the lakehouse directly)
⚠️ PySpark read access: Grant lakehouse item permission: Read + ReadAll. No workspace role needed. ReadAll = Spark can read table files. Without ReadAll, Spark can see the item but not the data.

🏛️ Data Warehouse — T-SQL, SCD, DDM & Security

Warehouse vs Lakehouse SQL Endpoint

  • Warehouse: supports CREATE, INSERT, UPDATE, DELETE, MERGE — full DW
  • Lakehouse SQL endpoint: READ ONLY — SELECT only, no writes
  • Cross-database: [warehouse_name].[schema].[table]

Slowly Changing Dimensions (SCD)

Type 0 — No change. Original data always preserved. No updates allowed.

Type 1 — Overwrite. Latest value only. No history tracked.
Type 2 — Full history. New row per change with StartDate, EndDate, IsCurrent. Point-in-time queries possible.

Type 3 — Previous value. Only one prior version stored in a column.
⚠️ SCD Type 2: Adds a NEW ROW for each change with Start Date + End Date. Type 1 overwrites (no history). Type 3 = one "previous value" column. Type 0 = no changes ever.

Dynamic Data Masking (DDM)

  • Masks data for unauthorized users — they see masked values (not an error)
  • Owner/sysadmin always sees real data
-- Mask entire column by data type (email → XXXX@XXXX.com, numbers → 0) ALTER TABLE t ALTER COLUMN email ADD MASKED WITH (FUNCTION = 'default()') -- Email masking: first letter + XXX@XXXX.com ALTER TABLE t ALTER COLUMN email ADD MASKED WITH (FUNCTION = 'email()') -- Partial: show first 2 chars, then "xxxxxx", then last 0 chars ALTER TABLE t ALTER COLUMN name ADD MASKED WITH (FUNCTION = 'partial(2,"xxxxxx",0)') -- Random: show random number between 1 and 1000 ALTER TABLE t ALTER COLUMN salary ADD MASKED WITH (FUNCTION = 'random(1,1000)')
⚠️ DDM partial(): partial(prefixSize, "padding", suffixSize). For first 2 + last 4: partial(2,"xxxx",4). For salary use random(). Cannot mask yourself or sysadmin.

GRANT / DENY / REVOKE

-- Grant SELECT on table GRANT SELECT ON dbo.TableName TO [role_or_user] -- Grant SELECT on specific columns only (Column-Level Security) GRANT SELECT ON dbo.TableName (col1, col2) TO [role_or_user] -- Deny (actively blocks, overrides GRANT) DENY SELECT ON dbo.TableName TO [role_or_user] -- Revoke (removes effect of both GRANT and DENY) REVOKE SELECT ON dbo.TableName FROM [role_or_user]
⚠️ REVOKE removes BOTH grant and deny. You cannot DENY/GRANT to: sysadmin, dbo, db_owner, information_schema, sys, or yourself.

Row-Level Security (RLS)

-- Step 1: Create filter predicate function (WITH SCHEMABINDING required) CREATE FUNCTION dbo.fn_security(@username AS sysname) RETURNS TABLE WITH SCHEMABINDING AS RETURN SELECT 1 AS result WHERE @username = DATABASE_PRINCIPAL_ID() OR SYSTEM_USER = @username -- Step 2: Create security policy CREATE SECURITY POLICY SalesFilter ADD FILTER PREDICATE dbo.fn_security(SalesPersonID) ON dbo.SalesTable WITH (STATE = ON)
⚠️ RLS requires a SECURITY POLICY with FILTER PREDICATE. Cannot block sysadmin/dbo/yourself.

Column-Level Security (CLS)

  • Grant SELECT only on specific columns
  • Users without column-level grant get permission error (not masked data — that's DDM)
GRANT SELECT ON dbo.Employee(EmployeeID, Name) TO [AuditorRole] -- Auditor can't SELECT Salary or Email — permission error if they try

Object-Level Security (OLS)

  • Simply do NOT grant SELECT on the table to the role
  • Users without GRANT cannot see or query the table at all
  • Different from RLS (row filtering) and CLS (column limiting)

queryinsights Views

  • sys.dm_exec_requests — queries currently running RIGHT NOW
  • queryinsights.exec_requests_history — all completed queries (30-day, ~15min delay)
  • queryinsights.long_running_queries — queries exceeding duration threshold
  • queryinsights.frequently_run_queries — most-executed query patterns
  • queryinsights.exec_sessions_history — session activity
⚠️ Real-time = sys.dm_exec_requests. History = queryinsights views. queryinsights has ~15 min delay and 30-day retention.

🔷 KQL — Kusto Query Language Reference

KQL Query Structure

  • Each | (pipe) passes the result of the previous operation to the next
  • Unlike SQL: no strict clause order — operations execute in pipe order
  • Table name comes first (no FROM keyword)
// Basic structure TableName | operator1 ... | operator2 ... | operator3 ...

Select & Project

// Select specific columns TableName | project col1, col2, col3 // Remove columns (keep all others) TableName | project-away col1, col2 // Rename columns TableName | project-rename NewName = OldName // Add calculated column TableName | extend FullName = FirstName + " " + LastName // Unique values TableName | distinct col1, col2 // Count total rows TableName | count

Filter & Limit

// Filter rows (use 'where' not 'filter') TableName | where col > 100 TableName | where col == "value" TableName | where col contains "substring" TableName | where col startswith "prefix" TableName | where col !~ "value" // case-insensitive not-equal // Limit rows TableName | take 10 TableName | limit 10 // same as take // Sort (default is descending) TableName | order by col asc TableName | sort by col desc
⚠️ Use where not filter in KQL. Default sort order is DESCENDING — add asc for ascending.

Time Filters

// Filter last 30 minutes TableName | where Timestamp > ago(30m) // Filter last 7 days TableName | where Timestamp > ago(7d) // Filter specific date range TableName | where Timestamp between (datetime(2026-01-01) .. datetime(2026-02-01)) // Time buckets (bin) TableName | summarize count() by bin(Timestamp, 1h) TableName | summarize count() by bin(Timestamp, 1d)

Aggregation

// Summarize (GROUP BY equivalent) TableName | summarize count() by Category TableName | summarize avg(Temperature), max(Temperature) by DeviceId TableName | summarize TotalSales = sum(Sales) by Region, Year // Count distinct TableName | summarize dcount(UserId) by Country // Percentile TableName | summarize percentile(Duration, 95) by Service

String Functions

// Case conversion | extend Upper = toupper(col), Lower = tolower(col) // Length | extend Len = strlen(col) // Substring | extend Sub = substring(col, 0, 5) // start at 0, take 5 chars // Split string into array | extend Parts = split(col, ",") // Replace | extend Clean = replace_regex(col, @"\s+", " ") // Contains check | where col contains "substring" | where col matches regex @"^\d{4}-\d{2}-\d{2}$"

DateTime Functions

// Current time | extend Now = now() // Extract parts | extend Year = datetime_part("year", Timestamp) | extend Month = datetime_part("month", Timestamp) // Add time | extend NextWeek = datetime_add("week", 1, Timestamp) // Difference | extend AgeDays = datetime_diff("day", now(), BirthDate)

Variables & Functions

// Let statement (variable) let threshold = 100; TableName | where Sales > threshold // Let with table let recentData = TableName | where Timestamp > ago(1h); recentData | summarize count() by Region // User-defined function .create function MyFunc(param: string) { TableName | where Category == param } // Call it: MyFunc("Electronics")

Joins & Union

// Join two tables Table1 | join kind=inner Table2 on $left.Key == $right.Key // Join kinds: inner, leftouter, rightouter, fullouter, leftanti, rightanti, leftsemi // Union (combine rows from multiple tables) union Table1, Table2 union withsource=TableName Table1, Table2 // adds column with source table name

KQL Database Commands

// Continuous export (stream data out to ADLS Gen2) .create-or-alter continuous-export MyExport over (TableName) to table ExternalTable // Create external table .create external table ExtTable (col1: string, col2: datetime) kind=adl dataformat=csv (h@'https://storage.dfs.core.windows.net/container;key') // Create materialized view (pre-aggregated) .create materialized-view MyView on table SourceTable { SourceTable | summarize count() by bin(Timestamp, 1h), DeviceId }
⚠️ Continuous export = .create-or-alter continuous-export. Different from .export to storage (one-time ad-hoc export).

Choosing a Streaming Engine

Eventstream
No-code interface like a pipeline
Real-time event routing + filtering
Millions of events/second
IoT, telemetry, clickstream
Can transform BEFORE destination
Spark Structured Streaming
Code-based (PySpark)
More complex transformations
Uses readStream / writeStream
Good for custom logic
Eventhouse / KQL Database
Time-series analytics, historical analysis
Best for: time-series, log analytics, IoT data
Query with KQL for real-time + historical

Eventstream Sources

  • Azure Event Hub
  • Azure IoT Hub
  • Azure Service Bus
  • Custom App (SDK)
  • Kafka
  • Amazon Kinesis
  • Google Pub/Sub
  • Sample data (built-in)

Eventstream Destinations

  • ✅ Lakehouse
  • ✅ KQL Database / Eventhouse
  • ✅ Warehouse
  • ✅ Activator (Reflex)
  • ✅ Custom App (SDK)
  • ✅ Eventstream (chain)

Eventstream Processor Nodes (transform IN FLIGHT)

  • Filter — pass only matching events (e.g., Status = 'Error')
  • Aggregate — compute aggregates over time windows
  • Group By — partition stream by column
  • Manage Fields — add/remove/rename columns
  • Union — combine two streams
  • Expand — flatten arrays/JSON
✅ To filter events before destination: Add a Filter processor node BETWEEN the source node and destination node in the Eventstream editor.

Windowing Functions in Eventstream

Tumbling — fixed-size, non-overlapping windows. Each event belongs to exactly one window.

Hopping — fixed-size, overlapping windows. Window starts every X seconds and lasts Y seconds. Events can belong to multiple windows.
Sliding — window slides with events. New window created when event enters or leaves.

Session — groups events with no more than X seconds gap between them. Window closes after inactivity.
⚠️ Window that starts every 5s and lasts 10s = Hopping window (overlapping). Tumbling = non-overlapping fixed. Session = based on inactivity gap.

Adjusting Eventstream Throughput

  • Method 1: Workspace ⋯ → Settings → Eventstream throughput
  • Method 2: Eventstream Home → wheel/settings icon → Throughput
  • Can only increase: Low → Medium → High. Cannot decrease without deleting and recreating.
  • Retention: default 1 day (24h), max 90 days
⚠️ TWO ways to change throughput: Workspace settings OR eventstream Home wheel icon.

Activator (Reflex)

  • Event-driven automation — monitors data and triggers actions when conditions are met
  • Triggers: Teams message, email, Power Automate flow, pipeline run
  • NOT a scheduler — it's event/condition-driven
  • Can be created from: Eventstream, KQL queryset, Power BI report
  • ❌ Cannot be created directly from Lakehouse
⚠️ Activator cannot be created from a Lakehouse. Use Eventstream → Activator destination, or from KQL queryset, or from Power BI report.

OneLake Event-Driven Pipeline

  • Trigger pipeline when files are added to a lakehouse folder (no polling)
  • Architecture: Files added → Eventstream monitors OneLake events → Activator checks condition → Triggers pipeline
  • Alternative to scheduled pipeline — runs on demand when data arrives

Eventhouse Status Monitoring

  • Running — operating optimally
  • Maintenance — temporarily unavailable (suspended capacity)
  • Suspended — capacity admin must reverse this
  • Unknown — unavailable for unknown reasons
  • Missing capacity — Fabric compute capacity exceeded
  • Hot cache — frequently accessed data in RAM (fast)
  • Cold cache/storage — less-used data on disk (slower but cheaper)

Spark Pool Types

Starter Pool
Quick start: 9–12 seconds
Libraries install quickly
Shuts down after 20 min inactivity
Use for: development environments
No configuration needed
Custom Pool
User-defined node size/count
Always on until manually paused
Supports autoscale

Spark Settings Location

  • Workspace Settings → Data Engineering/Science → Spark settings
  • Pool tab: create/manage pools
  • Environment tab: default environment, runtime version
  • High Concurrency tab: enable high concurrency mode

High Concurrency Mode

  • Same Spark session shared by multiple notebooks simultaneously
  • 36x faster session start vs standard spark session
  • Enable: Workspace Settings → Data Engineering/Science → Spark → High Concurrency tab

Domain Workspace Settings

  • Domains group workspaces for governance/discovery — metadata only
  • Domain assignment does NOT change permissions — workspace roles still control access
  • Domain admin can set policies (e.g., who can certify content in this domain)
  • Configure: Admin portal → Domains
⚠️ Assigning a workspace to a domain does NOT grant domain access permissions. Workspace roles remain the only access control mechanism.

Data Workflow Settings (Apache Airflow)

  • Used for orchestrating DAGs (Directed Acyclic Graphs)
  • Configure: Workspace Settings → Data Factory → Apache Airflow runtime settings
  • Starter pool: shuts down after 20min inactivity — for dev
  • Custom pool: always-on — for prod
  • Node sizes: Large (complex/production DAGs), Small (simple DAGs)
  • Autoscale: adds nodes dynamically as needed

Dataflow Gen2 Workspace Settings

  • Configure: Workspace Settings → Data Factory → Dataflow Gen2
  • Settings for refresh behavior, staging lakehouse

Fabric Capacity Metrics App

  • Install from AppSource — monitors capacity usage
  • Two tabs: Compute + Storage
  • Compute tab: CU (Capacity Unit) usage over time, throttling, smoothing, per-item breakdowns
  • Storage tab: OneLake storage consumption by workspace/item
  • Performance delta: compares fast operations (<200ms) now vs 7 days ago — higher = better performance
  • High CU: heavily used capacity or many operations running
⚠️ Capacity Metrics app has exactly TWO tabs: Compute and Storage.

Workspace Logging

  • Captures all item-level activity: creates, updates, deletes, runs — who did what and when
  • Logs stored as structured data in a designated lakehouse
  • Query logs in KQL (from the lakehouse)
  • Logging dashboards available via workspace logging feature
  • Enable: Workspace Settings → Workspace Logging
  • Used for: compliance, audit trails, security investigations
⚠️ Workspace logging (new Jan 2026 objective) is for item-level audit trails. Fabric Monitor is for real-time running jobs. queryinsights is for SQL query history.

Monitor Semantic Model Refresh

  • Monitor hub in workspace shows refresh history
  • Or: Workspace → semantic model ⋯ → Refresh history
  • Shows status (Success/Failed), duration, triggered by

Admin Portal — Tenant Settings

  • Who can change tenant settings: Fabric Admin, M365 Global Admin, Power Platform Admin
  • ❌ Capacity Administrator CANNOT change tenant settings
  • Block personal workspace reassignment: requires Fabric/Global/Power Platform admin
⚠️ Capacity Administrator cannot configure tenant settings — only Fabric Admin, M365 Global Admin, or Power Platform Admin can.

🔐 Security, Governance & Deployment Pipelines

Sensitivity Labels

  • Tell users about data sensitivity (Confidential, Public, Restricted, etc.)
  • Do NOT affect access to Fabric content
  • May affect access in Power BI Desktop
  • Applied to exported content: Excel, PDF, PowerPoint, PBIX download, Analyze in Excel, pivot table from semantic model
  • Apply via: item ⋯ → Settings → Sensitivity label, or Microsoft Purview catalog
  • Downstream inheritance: items created from labelled source automatically inherit same or higher label
⚠️ Downstream label inheritance: When a "Confidential" lakehouse is used as source, the downstream report/dataset automatically inherits "Confidential". Labels propagate automatically.

Endorsement

Promoted 🏅
Self-service endorsement
Any workspace Member or Admin can set it
Signals reliable, quality content
Access: workspace ⋯ → Settings → Endorsement
Certified ✅
Admin-controlled endorsement
Requires: Fabric Admin OR delegated certifier
Certifier delegated via Admin portal → Tenant settings → Certification

⚠️ Promoted = any Member/Admin. Certified = Fabric admin or delegated certifier ONLY. This distinction is heavily tested.

Access Control Summary

Feature Purpose How to implement
RLS (Row-Level Security) Filter rows by user T-SQL: CREATE SECURITY POLICY with FILTER PREDICATE
CLS (Column-Level Security) Block specific columns T-SQL: GRANT SELECT ON table(col1,col2) TO role
OLS (Object-Level Security) Hide entire table Simply do NOT grant SELECT on the table
DDM (Dynamic Data Masking) Show masked values ALTER TABLE…ADD MASKED WITH (FUNCTION = '...')
OLDAR (OneLake Data Access Roles) Folder-level path access Lakehouse → Manage → Security → define role with path

Deployment Pipelines

  • Create: workspace → Deployment pipelines (or via Deployment pipelines hub)
  • Stages: Development → Test → Production (can customize names)
  • Assign workspace to each stage (requires: workspace Admin)
  • Compare stages: requires pipeline admin + Contributor on workspace
⚠️ Credentials are NEVER copied between pipeline stages. After deployment, manually reconfigure data source credentials in each stage. This is the #1 deployment pipeline trap.
  • Deploy forward: Dev → Test → Prod
  • Deploy backward: only possible if target stage is empty (for retroactive setup)
  • Change indicator icon: appears when content changed since last deployment
  • Unsupported items: shown in UI but cannot be deployed (e.g., some custom items)
  • What IS copied: item definitions, schema, code, connection config structure
  • What is NOT copied: credentials, data, some sensitivity label settings

Git Integration

  • Supports: Azure DevOps, GitHub
  • GitHub setup requires 3 steps:
    1. Connect workspace to GitHub repo via Workspace Settings → Git integration
    2. Install Microsoft Fabric GitHub App on GitHub org/repo
    3. Authenticate with PAT or OAuth
  • Commit changes: Source control panel in workspace → Changes → Commit
  • Changes are NOT auto-committed — must be done manually
  • If Git connected: Save and Run instead of Publish button in Dataflow Gen2
⚠️ GitHub needs 3 steps: Connect workspace + install Fabric GitHub App + authenticate with PAT/OAuth. M365 admin centre is NOT involved.

Self-Hosted Integration Runtime (SHIR)

  • Required for: on-premises data sources (SQL Server, Oracle, SAP, etc.)
  • Installed on a machine in the private network
  • Creates secure OUTBOUND tunnel to Fabric — no inbound firewall rules needed
  • Azure IR: cloud/public endpoints only
  • Managed VNet IR: Azure private endpoints
⚠️ On-premises data source + no ExpressRoute = use SHIR. SHIR creates outbound connection — no inbound firewall changes needed.

Direct Lake — Fallback to DirectQuery

  • Direct Lake reads Delta table files directly — fastest mode for Power BI
  • Falls back to DirectQuery when: data volume exceeds the frame limit for the capacity SKU
  • Fix: upgrade to higher SKU (F8, F16, F32…) or reduce model size
  • V-Order does NOT cause fallback — it affects read speed only
  • Cross-workspace lakehouse: supported, no fallback
⚠️ Direct Lake fallback cause = frame limit exceeded by data volume. V-Order, cross-workspace access, or partition count do NOT cause fallback.
