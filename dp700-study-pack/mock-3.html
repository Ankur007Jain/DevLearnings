PART 1 (Q1–Q15)

Case study: Lakemont Energy (Q1–Q6)

Overview. Lakemont Energy is a regional electricity utility. It is moving billing and smart-meter analytics to Microsoft Fabric.

Existing environment - One F64 capacity. Workspaces LM-Dev, LM-Test and LM-Prod are the three stages of one deployment pipeline. - BillingDB is an Azure SQL Database (a writable primary, with a system-assigned managed identity on the server). Change data capture (CDC) is enabled on it. CDC was set up for a legacy integration that was retired last month, and nothing reads the change tables any more. - es-meters is an eventstream in LM-Prod. Its sources are Azure Event Hubs (meter events) and, since last week, an Azure SQL Database CDC source for the MeterRegistry table. Its destinations are lakehouse MeterLake (tables meter_events and meter_registry) and an Eventhouse. - BillingDW is a warehouse in LM-Prod. Pipeline pl-billing loads it every night with a Copy activity that has Enable staging turned on with Workspace staging. The load volume has doubled this quarter. - MeterLake has OneLake security enabled. Field analysts have no workspace role. The lakehouse was shared with them with “Read all Apache Spark” selected. A month ago a role named FieldUsage was created that grants them Read on Tables/usage_daily only. - Call-center agents have no workspace role. BillingDW is shared with them with no additional permissions.

Business requirements - BR1. BillingDB tables must be available in OneLake in near real time, with no ETL to build or maintain, and the replication itself must not consume capacity units. - BR2. Operations must be alerted when a meter reports more than 3 voltage-sag events within any 10-minute period. A result is wanted only when a meter’s count changes, not on a fixed schedule. - BR3. Call-center agents query BillingDW with T-SQL. They may see only customers in their own region. Any query of theirs that references the NationalId column must fail. They may see only the last four digits of AccountNumber.

Technical requirements - TR1. Field analysts must be able to read only usage_daily, from Spark notebooks. - TR2. Use least privilege and the least administrative effort.

Known issues - KI1. Field analysts can read every table in MeterLake from their notebooks. - KI2. When es-meters was published with the new CDC source, part of the MeterRegistry initial snapshot never reached meter_registry. The source and the destination show Active and report no errors. - KI3. The pl-billing Copy activity has failed on the last four nights, each time about 60 minutes after it started. Before the volume grew, it finished in about 40 minutes. Other, shorter copies in the same pipeline succeed.

Q1. You need to meet BR1. What should you do first? - A. Create the mirrored database for BillingDB now. Mirroring reuses the existing CDC capture. - B. Create a Copy job with CDC-based incremental copy and the Merge method, scheduled every 5 minutes. - C. Disable CDC on BillingDB, and then create a mirrored Azure SQL Database. - D. Create a OneLake shortcut to BillingDB in MeterLake.

Show answer

Answer: C. An Azure SQL database can’t be mirrored while CDC is enabled, so disable CDC first. Mirroring needs no ETL and its replication compute doesn’t consume capacity, which a Copy job does.
